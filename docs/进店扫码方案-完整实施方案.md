## 零、先读这一节：三个必须知道的结论

### 结论 1：后端能力比预期完整，不需要重写

你要的流程，**三个关键能力已经存在**：

| 能力 | 状态 | 位置 |
|------|------|------|
| 无房间下单 | ✅ 已支持 | `guest.js:128`（`room_id` 可选） |
| 待派钟队列 | ✅ 已实现 | `tickets.js:195` |
| 指派房间/技师 | ✅ 已实现 | `tickets.js:227`（含忙碌校验+审计） |
| 派单 UI | ✅ 已存在 | `PosHome.tsx:192-468` |
| AI 排钟推荐 | ✅ 已实现 | `ai.js:442` |

**而且**：`queue` 查询条件是 `technician_id IS NULL OR status='pending'`，
顾客不指定技师时 `technician_id` 为 NULL，**自动进待派队列**。这条链路已通。

### 结论 2：真正的地基缺口只有一个，且是现存 bug

```js
// guest.js:93  所有顾客端查询强制要 room_id
if (!room_id) throw new ValidationError('room_id required')
```

进店扫码时顾客**还没有房间**。下单后拿到 `ticket_id`，但：

- ❌ 没有 `GET /api/guest/tickets/:id` 端点
- ❌ 顾客刷新页面就找不到自己的单

**这个 bug 与是否做大堂码无关，现在就该修。**

### 结论 3：行业主流做法与一份调研报告相反（已在线查证）

| | 说法 |
|---|---|
| 子代理报告 | 点钟**不影响**轮转位置 |
| **在线查证（索易足道研究院，21年/10000+门店）** | 点钟优先制中，点钟技师**上完钟排回队尾** |

两种做法**都真实存在**，是门店可配置策略：

```
点钟排回队尾     ← 索易「点钟优先制」，需平衡收入
点钟不计入轮钟   ← 索易「提成+排钟双轨制」，提成已够激励
```

**结论：这应该是配置项，不是硬编码规则。**

## 一、方案总览

### 1.1 流程设计

```
【进店】顾客扫大堂码（不绑房间）
    ↓
【自助】选项目 → 可选指定技师（点钟）
    ↓
【提交】进入待派队列（无房间 / 可能有技师）
    ↓  ← 顾客端显示「等待安排房间」
【客服】看到队列 → 分配房间 + 确认/指派技师
    ↓
【开钟】顾客端自动切换到「服务进度」视图
    ↓
【服务中】加钟 / 点单 / 看进度
    ↓
【完成】评价
```

### 1.2 两种码并存，职责分离（有行业依据）

行业调研结论：**手牌体系的核心是「身份标识与位置解耦」**。

| | 大堂码 | 房间码（现有） |
|---|---|---|
| 场景 | 进店/等位 | 已入座 |
| 承载 | 选项目、点钟、下单 | 看进度、点单、加钟、评价 |
| 房间 | 客服分配 | 已绑定 |
| 依赖 | 无需房间 | 依赖房间 |

**为什么不合并成一个码**：房间码承载的「服务中」功能天然依赖房间；
大堂码承载的「下单前」功能天然无房间。硬合会两边都别扭。

### 1.3 职责边界（回答「谁决定什么」）

| 决策 | 谁定 | 理由 |
|------|------|------|
| 选什么项目 | 顾客 | 消费决策 |
| 要不要指定技师 | 顾客（可选） | 点钟是顾客权利 |
| **用哪个房间** | **客服** | 房间是运营资源，顾客无信息判断 |
| 顾客未指定时的技师 | 客服（按轮转） | 公平性由系统保证 |

**顾客选「项目 + 技师」，客服配「房间」。**

为什么房间必须客服分配（三个硬理由）：

1. **顾客无信息**：哪间空、什么类型、干净没有、是否预留，顾客不知道
2. **并发冲突**：两人同选一间，谁赢？锁的体验是"你选了但没了"
3. **运营动作**：VIP 预留、清洁周转、包间按容量安排，都是管理决策

### 阶段 0：补地基（必须先做）

**为什么必须最先做**：不做这个，后面所有顾客端功能都建在流沙上。

#### 0.1 新增单条查询端点

```
GET /api/guest/tickets/:id?t=<signed_token>
```

**鉴权设计**（调研推荐：URL 签名 Token）：

```js
// 生成（下单时返回）
const token = crypto.createHmac('sha256', JWT_SECRET)
  .update(`${ticket_id}:${shop_id}:${created_at}`)
  .digest('base64url')

// 校验（用 timingSafeEqual 防时序攻击）
function verifyGuestToken(token, ticketId, shopId, createdAt) {
  const expected = crypto.createHmac('sha256', JWT_SECRET)
    .update(`${ticketId}:${shopId}:${createdAt}`)
    .digest('base64url')
  return crypto.timingSafeEqual(Buffer.from(token), Buffer.from(expected))
}
```

**为什么需要签名而不是裸 ticket_id**：

`nanoid(12)` 空间约 4.7×10²¹，暴力猜中概率极低（按年 36500 单算约 7.8×10⁻¹⁸）。
**但**裸 ID 的弱点是**泄露**（URL 被截图、日志、Referer），签名 token 可绑定
`shop_id` + 过期时间，泄露后危害可控。

**必须做的校验**：

```js
// 1. 签名有效
// 2. token 中的 ticket_id === URL 中的 id（防 IDOR）
// 3. token 中的 shop_id === ticket.shop_id（防跨店）
// 4. 未过期
```

**脱敏要求**（调研指出，需评估）：

```js
// 不应返回给顾客端
customer_name    → 脱敏 张**
customer_phone   → 脱敏 138****5678
commission_cents → 完全不返回（技师提成与顾客无关）
notes            → 需评估（可能含内部备注）
```

### 阶段 2：排钟机制（新功能）

#### 2.1 先明确：现有 AI 推荐 ≠ 排钟

```
suggest-dispatch 评分  →「谁最合适」（评分/明星/负载/技能）
行业轮钟              →「谁该轮到」（公平轮转）
```

两者不冲突，**必须共存**：

| 场景 | 用哪个 |
|------|--------|
| 顾客指定技师（点钟） | 直接指派 |
| 顾客未指定，客服派单 | **轮转顺序**（公平） |
| 客服想优化配置 | AI 推荐（可选参考） |

**当前只有 AI 推荐**，后果：不指定技师的单，客服每次手动挑、倾向挑熟手
→ **老技师吃撑、新技师饿死**。

#### 2.2 行业标准排钟方式（在线查证，索易足道研究院）

| 方式 | 规则 | 适合 |
|------|------|------|
| **顺序轮排制** | 排固定队列，来客派队首，上完排队尾 | 小店（5人以下） |
| **点钟优先制** | 轮钟照常，点钟者调出队列上钟，**上完排回队尾** | 中小型 |
| 分等级轮排制 | 按等级分组，组内各自轮排 | 中大型（15人+） |
| 提成+排钟双轨制 | 轮钟/点钟不同提成，排钟上做平衡 | 中大型 |
| 预约优先制 | 预约优先占档期，散客穿插 | 高端/会员制 |

**原文关键提醒**：*"实际开店的，很少有用单一方式的，基本都是混合模式。"*

#### 2.3 本项目建议：从「点钟优先制」起步

理由：

1. **行业最常见**，索易列为中小型门店首选
2. **契合现有数据**：已有 `level`（初/中/高级）、`is_star`（明星技师）
3. **比纯顺序轮排更符合实际**：足浴店有明星技师体系
4. **比「分等级轮排」简单**：不需要重构定价体系

#### 2.4 数据建模（调研建议 + 我的修正）

```sql
-- technicians 表新增
ALTER TABLE technicians ADD COLUMN rotation_order INTEGER NOT NULL DEFAULT 0;
ALTER TABLE technicians ADD COLUMN rotation_active INTEGER NOT NULL DEFAULT 1;
ALTER TABLE technicians ADD COLUMN last_served_at INTEGER;

-- tickets 表新增（记录钟型）
ALTER TABLE tickets ADD COLUMN tick_type TEXT;           -- normal/point/extra
ALTER TABLE tickets ADD COLUMN parent_ticket_id TEXT;    -- 加钟关联原钟

-- 审计表
CREATE TABLE rotation_log (
  id TEXT PRIMARY KEY,
  shop_id TEXT NOT NULL,
  technician_id TEXT NOT NULL,
  ticket_id TEXT,
  action TEXT NOT NULL,        -- assigned/skipped/released
  created_at INTEGER NOT NULL
);
```

**⚠️ 关于「七种钟型」的重要修正**：

在线查证发现，**「挂钟」「留钟」「落钟」在公开网络找不到权威定义**：

| 术语 | 查证状态 |
|------|----------|
| 轮钟 / 点钟 / 加钟 | ✅ 有权威定义 |
| 上钟 / 下钟 / 排钟员 | ✅ 确认存在 |
| 挂钟 / 留钟 / 落钟 | ❌ 未找到权威定义 |
| 跳钟 | ⚠️ **两种矛盾定义**（见下） |

**「跳钟」的定义分歧**：

```
说法 A（百度文库）：顾客临场改选技师 →「跳钟不算点钟，被放弃的技师仍排回原位」
说法 B（子代理报告）：技师在忙被系统跳过
```

**建议**：不要沿用有歧义的术语做字段名。用明确命名：

```
tech_busy_skip    技师在忙被跳过（系统行为）
customer_switch   顾客临场改选（顾客行为）
```

**不要为了凑齐七种术语而引入没有实际用途的字段。**

#### 2.5 轮转算法核心

```sql
-- 选下一个该上钟的技师
SELECT id, rotation_order FROM technicians
WHERE shop_id=? AND active=1 AND status='idle' AND rotation_active=1
ORDER BY rotation_order ASC
LIMIT 1;
```

派单后：

```sql
-- 排到队尾
UPDATE technicians
SET rotation_order = (SELECT COALESCE(MAX(rotation_order),0)+1 FROM technicians WHERE rotation_active=1),
    last_served_at = ?,
    updated_at = ?
WHERE id = ?;
```

**并发安全**（调研建议）：用 `BEGIN IMMEDIATE` 事务，避免两个客服同时派给同一技师。

```js
// better-sqlite3 已是同步事务，注意用 immediate
db.prepare('BEGIN IMMEDIATE').run()
try { /* 选人 + 派单 + 更新顺序 */ db.prepare('COMMIT').run() }
catch (e) { db.prepare('ROLLBACK').run(); throw e }
```

**⚠️ 需注意**：本项目 `changeStatus` 已有事务包裹，新增轮转逻辑要**并入同一事务**，
不能嵌套独立事务（SQLite 不支持嵌套）。

#### 2.6 一个需要用户决策的产品问题

本项目 `level` 字段（初级/中级/高级）和 `is_star`（明星技师）**不参与定价**
（`services.price_cents` 统一）。

而行业「分等级轮排制」要求**每个等级价格不同**。

**所以本项目当前数据模型不支持分等级轮排** —— 除非改造定价体系。
**这是产品决策，不是技术问题。**

### 阶段 3：顾客端状态联动

客服配房后，顾客端从「等待中」切到「服务进度」。

**调研推荐 SSE（Server-Sent Events）替代 WebSocket**：

理由：现有 WebSocket 需 JWT（`bus.js:20`），顾客无 token。

**我的评估**：现有顾客端已是 **10 秒轮询**（`GuestView.tsx:74`），
对「等待分配房间」这个场景**轮询完全够用**（顾客不会盯着屏幕）。

**建议**：阶段 3 先不做 SSE，保持轮询。等有实际性能问题再优化。
**理由**：本地单机部署，轮询压力可忽略；SSE 需要新的鉴权通道，增加复杂度。

## 三、局域网扫码的技术约束（重要，有硬限制）

### 3.1 已查证的事实

| 项 | 结论 |
|---|---|
| 二维码 URL | `http://<局域网IP>:8080/guest/lobby` |
| IP 固定 | 路由器 DHCP 静态分配 或 主机静态 IP |
| 微信扫码 | ✅ 可打开 HTTP 局域网地址，**支持非标准端口** |
| 微信支付 | ❌ 需 HTTPS |
| Service Worker | ❌ **HTTP 局域网下无法注册**（非安全上下文） |
| 语音识别 | ⚠️ 行为不一致，可能不可用 |
| 自签名 HTTPS | ❌ 不推荐（iOS 需手动装证书，体验差） |

### 3.2 对本项目的直接影响

**项目已有 `VoiceInput` 语音点单组件** —— 在 HTTP 局域网下**可能失效**。

**必须验证**：实测店内手机上语音点单是否可用，不可用则提供手动输入降级
（代码里已有降级逻辑，见 `GuestOrderSheet.tsx:72-81` 的 `matchItemByName`）。

**PWA 离线能力受限**：Service Worker 无法注册 → 断网时无离线兜底。
但局域网本身很快，这个限制可接受。

### 3.3 二维码 IP 变化的容错

**风险**：路由器重启导致 IP 变化 → 二维码失效。

**建议**：
1. 路由器设置 DHCP 静态分配（一劳永逸）
2. 后台管理页显示当前二维码 + IP（便于重新打印）
3. 项目已有 `getLanIPs()`（`lib/network.js`），可直接复用生成二维码

## 五、上线策略（调研建议）

```
阶段一：1-2 个门店试点，面向年轻顾客
阶段二：扩大试点，增加老年顾客引导
阶段三：全面推广
```

**关键风险（调研指出）**：*"先下单后分配"的最大风险是顾客等待时间不透明
导致焦虑和流失，必须提供实时排队位次和预估等待时间。*

**所以顾客等待页必须显示**：

```
✓ 排队位次（前面还有 2 位）
✓ 预估等待时间（约 15 分钟）
✓ 当前状态（等待客服安排房间）
```

预估等待时间的算法（调研建议）：

```
预计等待 = 技师当前钟剩余时长 + 加钟预计时长
```

## 七、需要用户决策的问题

1. **点钟是否计入轮转？**
   - A. 点钟后排回队尾（索易「点钟优先制」）
   - B. 点钟不计入轮转（索易「双轨制」）

   - 现状：所有技师同价，`level` 字段不参与定价
   - 若要做分等级轮排，需先改造定价体系（产品决策）
