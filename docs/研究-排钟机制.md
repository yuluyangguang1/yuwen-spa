## 一、七种钟型的精确定义与语义

### 1.1 轮钟（轮转钟）

| 项目 | 说明 |
|------|------|
| **定义** | 按轮转顺序自动分配给下一个空闲技师的钟，顾客不指定技师 |
| **触发条件** | 顾客下单时不指定 technician_id，系统按轮转队列自动派单 |
| **提成影响** | 无额外提成，按基础单价计算 |
| **对轮转的影响** | 轮钟完成后，该技师排到队尾（或按权重调整位置） |
| **行业差异** | 部分门店轮钟有保底提成，部分完全无额外激励 |

### 1.2 点钟（指定钟）

| 项目 | 说明 |
|------|------|
| **定义** | 顾客指定某位技师服务，该技师跳过轮转直接上钟 |
| **触发条件** | 顾客在下单时选择特定 technician_id |
| **提成影响** | 通常有额外提成（点钟费/点钟奖），行业常见做法是点钟单价上浮 10%-30% 或固定加 10-30 元 |
| **对轮转的影响** | 点钟**不改变**该技师的轮转位置（即点钟不算"轮到"，轮转顺序不变）。这是最常见的做法，但部分门店会让点钟后技师排到队尾 |
| **行业差异** | ① 主流做法：点钟不影响轮转位置；② 部分门店：点钟后技师排到队尾（类似"用掉一次轮转机会"） |

### 1.3 加钟（续钟）

| 项目 | 说明 |
|------|------|
| **定义** | 顾客在同一技师服务结束后，要求延长服务时间或增加项目 |
| **触发条件** | 技师当前钟未完成，顾客提出加钟请求 |
| **提成影响** | 加钟部分按正常单价计算，部分门店加钟有额外提成激励 |
| **对轮转的影响** | 加钟**不影响**轮转位置。技师仍在服务中，加钟结束后才重新进入轮转队列 |
| **行业差异** | 部分门店加钟算作独立的一钟（影响轮转），但主流做法是加钟不改变轮转 |

### 1.4 落钟（掉钟/漏钟）

| 项目 | 说明 |
|------|------|
| **定义** | 技师因各种原因未能按时上钟，导致该轮转机会"落空" |
| **触发条件** | 技师请假、迟到、临时有事、联系不上等 |
| **提成影响** | 无收入，该轮转机会作废 |
| **对轮转的影响** | 落钟后技师**保留**在轮转队列中的位置不变（即这次不算轮到，下次继续轮到该技师）。部分门店会让落钟技师排到队尾 |
| **行业差异** | ① 主流：落钟不改变轮转位置；② 部分门店：落钟后技师排到队尾作为"惩罚" |

### 1.5 跳钟（跳过钟）

| 项目 | 说明 |
|------|------|
| **定义** | 轮转到某技师时，该技师正在服务中（或在忙/休息），系统跳过该技师，分配给下一位 |
| **触发条件** | 轮转队列中下一个技师状态为 working/break |
| **提成影响** | 无收入，该轮转机会被跳过 |
| **对轮转的影响** | 跳钟后，被跳过的技师**保留**在轮转队列中的位置（下次轮转时优先分配给该技师）。这是为了保证公平——技师不是因为自己的原因被跳过，不应因此失去机会 |
| **行业差异** | 部分门店跳钟后技师排到队尾，但主流做法是保留位置 |

### 1.6 挂钟（挂起钟）

| 项目 | 说明 |
|------|------|
| **定义** | 技师暂时无法上钟（如正在服务、休息、外出），主动或被动"挂起"轮转资格 |
| **触发条件** | 技师主动申请挂起（如吃饭、休息）或系统检测到技师不可用 |
| **提成影响** | 无收入，轮转暂停 |
| **对轮转的影响** | 挂起期间不参与轮转，挂起结束后**恢复到挂起前的位置**（不排到队尾） |
| **行业差异** | 部分门店挂起超过一定时间后重新排到队尾 |

### 1.7 留钟（保留钟）

| 项目 | 说明 |
|------|------|
| **定义** | 门店或客服主动为特定技师"保留"一个轮转机会，通常用于新技师入职、老技师回归等场景 |
| **触发条件** | 新技师入职需要快速积累经验；老技师回归需要恢复状态；门店激励政策 |
| **提成影响** | 按正常轮钟计算 |
| **对轮转的影响** | 留钟相当于给该技师一个"虚拟轮转机会"，不影响其他技师的轮转顺序 |
| **行业差异** | 留钟不是所有门店都有，属于管理激励手段 |

### 1.8 钟型对比总结

| 钟型 | 顾客指定 | 额外提成 | 影响轮转位置 | 典型场景 |
|------|---------|---------|-------------|---------|
| 轮钟 | 否 | 无 | 完成后排到队尾 | 正常派单 |
| 点钟 | 是 | 有 | 不影响（主流） | 顾客指定技师 |
| 加钟 | 否 | 可能有 | 不影响 | 延长服务 |
| 落钟 | 否 | 无 | 不影响（主流） | 技师缺席 |
| 跳钟 | 否 | 无 | 不影响（主流） | 技师在忙 |
| 挂钟 | 否 | 无 | 不影响 | 技师休息 |
| 留钟 | 否 | 无 | 不影响 | 新技师/激励 |

## 二、轮钟算法的公平性设计

### 2.1 轮转队列（Round-Robin）基本实现

**核心思想**：维护一个有序的技师队列，每次派单时选择队首的可用技师，派单后将其移到队尾。

**基本流程**：
```
1. 获取当前轮转队列（按 rotation_order 排序）
2. 从队首开始，找到第一个状态为 idle 的技师
3. 派单给该技师
4. 将该技师的 rotation_order 更新为当前最大值 + 1（排到队尾）
5. 记录 last_served_at = 当前时间
```

### 2.2 公平性保证机制

#### 2.2.1 避免老技师被跳过

- **跳钟补偿**：技师因在忙被跳过后，下次轮转时优先分配（不排到队尾）
- **落钟补偿**：技师因请假落钟后，下次轮转时优先分配
- **挂起恢复**：技师挂起结束后恢复到挂起前的位置

#### 2.2.2 新技师吃不到钟

- **留钟机制**：新技师入职时，系统自动为其分配若干"留钟"机会
- **等级权重**：新技师（初级）可以设置更高的轮转权重，使其更频繁地被分配
- **保底机制**：新技师入职前 N 天，保证每天至少 X 个钟

#### 2.2.3 点钟对轮转位置的影响

**推荐做法（主流）**：点钟**不改变**轮转位置。

**理由**：
- 点钟是顾客主动选择，不是技师"轮到"的机会
- 如果点钟后排到队尾，会导致点钟多的技师（通常是技术好的）反而轮钟机会减少，不公平
- 点钟本身已有额外提成，不需要再通过轮转位置补偿

**替代做法**：点钟后排到队尾。适用于点钟提成较低、需要平衡技师收入的门店。

#### 2.2.4 加钟对轮转位置的影响

**推荐做法**：加钟**不改变**轮转位置。

**理由**：
- 加钟是同一技师服务的延续，技师仍在服务中
- 加钟结束后，技师自然回到轮转队列的当前位置
- 如果加钟后排到队尾，会导致顾客想加钟时技师不愿意（因为会失去轮转位置）

#### 2.2.5 跳钟补偿机制

**推荐做法**：跳钟后，被跳过的技师**保留**在轮转队列中的位置。

**实现方式**：
- 技师状态变为 working/break 时，不改变其 rotation_order
- 下次轮转时，如果该技师已恢复 idle 状态，优先分配
- 如果该技师仍在忙，继续跳过

#### 2.2.6 技师上班/下班/请假处理

**上班（加入轮转队列）**：
- 技师状态变为 idle 时，将其 rotation_order 设置为当前队列中间位置（避免一开始就排到队首或队尾）
- 或者设置为当前最小值 - 1（排到队首，快速开始接单）

**下班（退出轮转队列）**：
- 技师状态变为 off 时，从轮转队列中移除（或标记为不参与轮转）
- 如果技师有未完成的钟，等待完成后移除

**请假（临时退出）**：
- 技师状态变为 break 时，保留在轮转队列中，但跳过分配
- 请假结束后，恢复到请假前的位置

#### 2.2.7 技师等级对轮转权重的影响

**推荐做法**：等级**不直接影响**轮转顺序，但可以通过以下方式间接影响：

- **点钟率**：高级技师点钟率高，自然收入高
- **加钟率**：高级技师加钟率高，自然收入高
- **轮钟权重**：如果需要平衡收入，可以设置初级技师的轮转权重更高（如初级技师轮 2 次，高级技师轮 1 次）

**不推荐**：直接按等级排序轮转，会导致高级技师（通常技术好、点钟多）轮钟机会减少，可能引发不满。

### 2.3 轮转算法伪代码

```python
def assign_next_technician():
    """
    从轮转队列中选择下一个该上钟的技师
    """
    # 1. 获取所有参与轮转的技师（状态为 idle）
    candidates = db.query("""
        SELECT id, rotation_order, level, years, ai_score
        FROM technicians
        WHERE status = 'idle'
          AND rotation_active = 1
        ORDER BY rotation_order ASC
    """)
    
    if not candidates:
        return None  # 无可用技师
    
    # 2. 选择队首的技师
    next_tech = candidates[0]
    
    # 3. 更新轮转位置（排到队尾）
    max_order = db.query("SELECT MAX(rotation_order) FROM technicians WHERE rotation_active = 1")
    new_order = max_order + 1
    
    db.execute("""
        UPDATE technicians
        SET rotation_order = ?,
            last_served_at = datetime('now'),
            rotation_skip_count = 0
        WHERE id = ?
    """, (new_order, next_tech.id))
    
    # 4. 记录派单历史
    db.execute("""
        INSERT INTO rotation_log (technician_id, ticket_id, action, created_at)
        VALUES (?, ?, 'assigned', datetime('now'))
    """, (next_tech.id, ticket_id))
    
    return next_tech
```

## 三、排钟与房间的联合调度

### 3.1 先选技师还是先选房间？

**推荐做法**：先选技师，再选房间。

**理由**：
- 技师是核心资源，房间是辅助资源
- 顾客通常更关心技师（尤其是点钟时）
- 房间通常比技师多，更容易找到空闲房间

**流程**：
```
1. 根据轮转算法选择技师
2. 根据技师状态和房间可用性，分配合适的房间
3. 如果无可用房间，技师保持 idle 状态，等待房间释放
```

### 3.2 顾客点钟但技师在忙时的等待时间估算

**估算公式**：
```
预计等待时间 = 技师当前钟的剩余时长 + 技师当前钟的加钟预计时长
```

**实现方式**：
```sql
-- 查询技师当前钟的剩余时长
SELECT 
    t.id,
    t.start_time,
    t.duration_minutes,
    t.status,
    CASE 
        WHEN t.status = 'active' THEN 
            MAX(0, t.duration_minutes - (julianday('now') - julianday(t.start_time)) * 24 * 60)
        ELSE 0
    END AS remaining_minutes
FROM tickets t
WHERE t.technician_id = ?
  AND t.status IN ('active', 'pending')
ORDER BY t.created_at DESC
LIMIT 1;
```

**优化**：
- 如果技师有多个待完成的钟，累加所有剩余时长
- 考虑技师的历史平均服务时长（而非标准时长）
- 提供"预计等待时间"给顾客，让顾客决定是否等待

### 3.3 多个待派单同时到达时的派单顺序

**推荐策略**：
1. **点钟优先**：顾客指定的钟优先派单（因为顾客有明确期望）
2. **等待时间长的优先**：等待时间长的订单优先派单（避免顾客流失）
3. **VIP 优先**：VIP 顾客的订单优先派单
4. **轮钟按顺序**：轮钟订单按下单时间顺序派单

**实现方式**：
```sql
-- 获取待派单队列，按优先级排序
SELECT 
    t.id,
    t.customer_id,
    t.technician_id,
    t.created_at,
    t.is_vip,
    CASE 
        WHEN t.technician_id IS NOT NULL THEN 1  -- 点钟优先
        WHEN t.is_vip = 1 THEN 2                 -- VIP 优先
        ELSE 3                                    -- 普通轮钟
    END AS priority
FROM tickets t
WHERE t.status = 'pending'
  AND t.technician_id IS NULL  -- 只处理未指定技师的订单
ORDER BY priority ASC, t.created_at ASC;
```

## 四、数据建模建议（SQLite 表结构）

### 4.1 technicians 表新增字段

```sql

ALTER TABLE technicians ADD COLUMN rotation_skip_count INTEGER DEFAULT 0;
ALTER TABLE technicians ADD COLUMN rotation_weight INTEGER DEFAULT 1;  -- 轮转权重（用于等级平衡）

```

**字段说明**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `rotation_order` | INTEGER | 轮转顺序，值越小越优先 |
| `rotation_active` | INTEGER | 是否参与轮转（1=是，0=否） |
| `last_served_at` | DATETIME | 上次上钟时间 |
| `rotation_skip_count` | INTEGER | 被跳过次数（用于补偿） |
| `rotation_weight` | INTEGER | 轮转权重（初级=2，中级=1，高级=1） |
| `on_duty_at` | DATETIME | 当天上班时间 |
| `off_duty_at` | DATETIME | 当天下班时间 |

### 4.2 是否需要独立的排钟队列表？

**推荐做法**：**不需要**独立队列表，使用 technicians 表的字段即可。

**理由**：
- 技师数量通常不多（10-50 人），单表查询性能足够
- 轮转队列是技师列表的子集，不需要额外维护
- 减少数据一致性风险

**如果技师数量超过 100 人**，可以考虑独立队列表：

```sql
-- 独立轮转队列表（可选，技师数量大时使用）
CREATE TABLE rotation_queue (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    technician_id INTEGER NOT NULL UNIQUE,
    rotation_order INTEGER NOT NULL,
    rotation_weight INTEGER DEFAULT 1,
    is_active INTEGER DEFAULT 1,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (technician_id) REFERENCES technicians(id)
);

CREATE INDEX idx_rotation_queue_order ON rotation_queue(rotation_order);
CREATE INDEX idx_rotation_queue_active ON rotation_queue(is_active);
```

**tick_type 枚举值**：

| 值 | 说明 |

### 4.4 点钟跳过轮转的历史记录表

```sql
-- 点钟历史记录表（用于审计和统计）
CREATE TABLE point_ticket_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,

    technician_id INTEGER NOT NULL,
    customer_id INTEGER,
    point_premium REAL DEFAULT 0,

    FOREIGN KEY (ticket_id) REFERENCES tickets(id),
    FOREIGN KEY (technician_id) REFERENCES technicians(id)
);

-- 轮转历史记录表（用于审计和统计）
CREATE TABLE rotation_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    ticket_id INTEGER,
    technician_id INTEGER NOT NULL,
    action TEXT NOT NULL,  -- assigned, skipped, missed, extra, reserved
    reason TEXT,  -- 跳过/落钟原因
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (ticket_id) REFERENCES tickets(id),
    FOREIGN KEY (technician_id) REFERENCES technicians(id)
);

CREATE INDEX idx_rotation_log_tech ON rotation_log(technician_id);
CREATE INDEX idx_rotation_log_time ON rotation_log(created_at);
```

```sql
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (technician_id) REFERENCES technicians(id),
    FOREIGN KEY (parent_ticket_id) REFERENCES tickets(id)
);

-- 点钟历史记录表
CREATE TABLE point_ticket_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    ticket_id INTEGER NOT NULL,
    technician_id INTEGER NOT NULL,
    customer_id INTEGER,
    point_premium REAL DEFAULT 0,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (ticket_id) REFERENCES tickets(id),
    FOREIGN KEY (technician_id) REFERENCES technicians(id)
);

-- 轮转历史记录表
CREATE TABLE rotation_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    ticket_id INTEGER,
    technician_id INTEGER NOT NULL,
    action TEXT NOT NULL,
    reason TEXT,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (ticket_id) REFERENCES tickets(id),
    FOREIGN KEY (technician_id) REFERENCES technicians(id)
);
```

## 五、实现要点

### 5.1 轮转排序 SQL 查询示例

```sql
-- 查询下一个该上钟的技师
SELECT 
    t.id,
    t.number,
    t.name,
    t.level,
    t.years,
    t.rotation_order,
    t.rotation_weight,
    t.last_served_at,
    t.rotation_skip_count
FROM technicians t
WHERE t.status = 'idle'
  AND t.rotation_active = 1
ORDER BY t.rotation_order ASC
LIMIT 1;

-- 查询技师的轮转统计（用于公平性分析）
SELECT 
    t.id,
    t.name,
    t.level,
    COUNT(CASE WHEN r.action = 'assigned' THEN 1 END) AS assigned_count,
    COUNT(CASE WHEN r.action = 'skipped' THEN 1 END) AS skipped_count,
    COUNT(CASE WHEN r.action = 'missed' THEN 1 END) AS missed_count,
    COUNT(CASE WHEN r.action = 'extra' THEN 1 END) AS extra_count,
    MAX(r.created_at) AS last_rotation_time
FROM technicians t
LEFT JOIN rotation_log r ON t.id = r.technician_id
WHERE t.rotation_active = 1
GROUP BY t.id
ORDER BY assigned_count DESC;
```

### 5.2 并发安全：避免重复派单

**问题**：多个客服同时派钟时，可能将同一个技师分配给多个订单。

**解决方案**：使用数据库事务 + 乐观锁

```sql
-- 事务开始
BEGIN TRANSACTION;

-- 1. 查询并锁定技师（使用 FOR UPDATE）
SELECT id, rotation_order
FROM technicians
WHERE status = 'idle'
  AND rotation_active = 1
ORDER BY rotation_order ASC
LIMIT 1
FOR UPDATE;

-- 2. 更新技师状态为 working
UPDATE technicians
SET status = 'working',
    rotation_order = (SELECT MAX(rotation_order) FROM technicians WHERE rotation_active = 1) + 1,
    last_served_at = datetime('now')
WHERE id = ?;

-- 3. 创建钟单
INSERT INTO tickets (customer_id, technician_id, status, tick_type, created_at)
VALUES (?, ?, 'active', 'normal', datetime('now'));

-- 4. 记录轮转日志
INSERT INTO rotation_log (ticket_id, technician_id, action, created_at)
VALUES (?, ?, 'assigned', datetime('now'));

-- 提交事务
COMMIT;
```

**注意**：SQLite 的 `FOR UPDATE` 语法不支持，但可以使用 `BEGIN IMMEDIATE` 事务来保证原子性：

```sql
BEGIN IMMEDIATE;
-- 执行上述操作
COMMIT;
```

### 5.3 技师状态与轮转队列同步

**状态变更时的处理**：

| 状态变更 | 轮转队列操作 |
|---------|-------------|
| off → idle（上班） | 设置 rotation_order = 当前最小值 - 1（排到队首） |
| idle → working（上钟） | 更新 rotation_order = 当前最大值 + 1（排到队尾） |
| working → idle（下钟） | 不改变 rotation_order（已在队尾） |
| idle → break（休息） | 不改变 rotation_order，但跳过分配 |
| break → idle（恢复） | 不改变 rotation_order，恢复分配 |
| idle → off（下班） | 设置 rotation_active = 0（退出轮转） |

**触发器实现**：

```sql
-- 技师状态变更触发器
CREATE TRIGGER technician_status_change
AFTER UPDATE OF status ON technicians
BEGIN
    -- 上班时加入轮转队列
    IF NEW.status = 'idle' AND OLD.status = 'off' THEN
        UPDATE technicians
        SET rotation_order = (SELECT MIN(rotation_order) FROM technicians WHERE rotation_active = 1) - 1,
            rotation_active = 1
        WHERE id = NEW.id;
    END IF;
    
    -- 下班时退出轮转队列
    IF NEW.status = 'off' AND OLD.status != 'off' THEN
        UPDATE technicians
        SET rotation_active = 0
        WHERE id = NEW.id;
    END IF;
    
    -- 上钟时更新轮转位置
    IF NEW.status = 'working' AND OLD.status = 'idle' THEN
        UPDATE technicians
        SET rotation_order = (SELECT MAX(rotation_order) FROM technicians WHERE rotation_active = 1) + 1,
            last_served_at = datetime('now')
        WHERE id = NEW.id;
    END IF;
END;
```

### 5.4 点钟处理逻辑

```sql
-- 点钟派单（顾客指定技师）
BEGIN IMMEDIATE;

-- 1. 检查技师是否可用
SELECT status FROM technicians WHERE id = ?;

-- 2. 如果技师可用，直接派单
UPDATE technicians
SET status = 'working',
    last_served_at = datetime('now')
WHERE id = ?;

-- 3. 创建点钟记录
INSERT INTO tickets (customer_id, technician_id, status, tick_type, is_point_ticket, point_premium, created_at)
VALUES (?, ?, 'active', 'point', 1, ?, datetime('now'));

-- 4. 记录点钟历史
INSERT INTO point_ticket_log (ticket_id, technician_id, customer_id, point_premium, created_at)
VALUES (?, ?, ?, ?, datetime('now'));

COMMIT;
```

**注意**：点钟**不改变** rotation_order（主流做法）。

### 5.5 跳钟处理逻辑

```sql
-- 跳钟处理（技师在忙）
BEGIN IMMEDIATE;

-- 1. 记录跳钟日志
INSERT INTO rotation_log (ticket_id, technician_id, action, reason, created_at)
VALUES (?, ?, 'skipped', 'technician_busy', datetime('now'));

-- 2. 增加跳过次数（用于补偿）
UPDATE technicians
SET rotation_skip_count = rotation_skip_count + 1
WHERE id = ?;

-- 3. 不改变 rotation_order（保留位置）

COMMIT;
```

### 5.6 加钟处理逻辑

```sql
-- 加钟处理
BEGIN IMMEDIATE;

-- 1. 创建加钟记录（关联原钟）
INSERT INTO tickets (customer_id, technician_id, status, tick_type, parent_ticket_id, created_at)
VALUES (?, ?, 'active', 'extra', ?, datetime('now'));

-- 2. 不改变技师的 rotation_order（加钟不影响轮转）

COMMIT;
```

## 六、总结与建议

### 6.1 推荐配置

| 配置项 | 推荐值 | 理由 |
|--------|--------|------|
| 点钟影响轮转 | 不影响 | 主流做法，公平合理 |
| 加钟影响轮转 | 不影响 | 技师仍在服务中 |
| 跳钟补偿 | 保留位置 | 保证公平 |
| 落钟补偿 | 保留位置 | 保证公平 |
| 挂起恢复 | 恢复原位置 | 保证公平 |
| 等级权重 | 不直接影响 | 通过点钟/加钟自然平衡 |
| 新技师保护 | 留钟机制 | 快速积累经验 |

### 6.2 实现优先级

1. **P0（必须）**：轮转队列基本逻辑、点钟派单、状态同步
2. **P1（重要）**：跳钟补偿、落钟补偿、加钟处理
3. **P2（优化）**：等待时间估算、派单优先级、统计分析

### 6.3 注意事项

1. **并发安全**：使用 `BEGIN IMMEDIATE` 事务保证原子性
2. **数据一致性**：技师状态与轮转队列保持同步
3. **审计日志**：记录所有轮转操作，便于排查问题
4. **灵活性**：提供配置选项，允许门店自定义规则
5. **性能优化**：技师数量大时，考虑独立队列表

## 附录：行业差异说明

由于不同地区、不同规模的门店可能有不同的排钟规则，以下是一些常见的差异点：

1. **点钟是否影响轮转**：主流做法是不影响，但部分门店会让点钟后排到队尾
2. **跳钟补偿**：主流做法是保留位置，但部分门店会让跳钟后排到队尾
3. **提成比例**：点钟提成比例因门店而异，通常为 10%-30%
4. **等级权重**：部分门店会直接按等级排序轮转，但主流做法是不直接影响
5. **新技师保护**：部分门店有留钟机制，部分门店没有

**建议**：在系统中提供配置选项，允许门店根据自身情况自定义规则。
