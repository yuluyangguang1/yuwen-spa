## 一、真实业务链路（据店主口述）

```
【获客阶段 — 店外】
  散客：抖音/美团搜到店铺 → 看评分/项目/技师 → 线上下单 → 到店核销
  会员：直接到店报手机号 → 小充值（几百）或大额充值（几万）

【接待阶段 — 到店】
  客服迎接 → 带领至房间 → 客服推荐项目
  → 客人选项目 或 核销抖音/美团团购券
  → 客服安排技师（人工指派 或 按排钟顺序）

【服务阶段 — 房间内】
  【可换技师】客人对技师不满意 → 换技师
  技师分级：明星技师 / 普通技师（影响价格与排钟优先级）
  技师开始项目 → 计时
  期间客人可手机扫码点餐 / 购买商品
  技师服务完毕 → 请客人评价

【离店阶段】
  如需夜晚留宿 → 告知店里登记
  结账离店
```

**关键洞察**：这是一条 **"获客 → 接待 → 服务 → 离店"** 的完整链路，
而本项目目前的实现集中在 **"服务 → 离店"** 这一段（开钟/派钟/结账/报表）。
**前后两端都是缺口**：获客端的团购核销，接待端的客服工作台。

## 三、P0 缺口详析

### P0-1 抖音/美团团购券核销 ★最高优先级

**为什么是最高优先级**：店主明确说"散客获客是在抖音美团上搜到店铺"。
这是**散客的唯一入口**，而代码里完全不存在。目前只能靠客服手工登记，无法对账。

**现有基础**：`coupons` 表已存在，但结构不匹配：

```sql
-- 现有 coupons 表（自营销券）
type    TEXT  -- percent | fixed
value   INTEGER
code    TEXT  -- 券码
max_uses INTEGER
```

**缺的是"平台券"这个品类**，它和自营销券有本质差异：

| 维度 | 自营销券（现有） | 平台团购券（缺失） |
|------|------------------|-------------------|
| 来源 | 本店发放 | 抖音/美团平台 |
| 核销方式 | 输入券码 | **扫码核销 / 手动输码** |
| 结算 | 无 | **平台月结，需对账** |
| 套餐 | 单项目折扣 | **组合套餐**（如"足疗60min+采耳"） |
| 退款 | 本店处理 | **平台发起，需同步状态** |
| 数据 | 本店自有 | 需记录平台订单号 |

**建议设计**：

```sql
CREATE TABLE platform_vouchers (
  id                TEXT PRIMARY KEY,
  shop_id           TEXT NOT NULL REFERENCES shops(id),
  platform          TEXT NOT NULL,      -- douyin | meituan | other
  platform_order_no TEXT,               -- 平台订单号（对账用）
  code              TEXT,               -- 核销码
  package_name      TEXT,               -- 套餐名（如"足疗60分钟"）
  face_value_cents  INTEGER NOT NULL,   -- 面值（客人付给平台的）
  settle_value_cents INTEGER NOT NULL,  -- 平台结算给本店的（扣除佣金后）
  status            TEXT NOT NULL DEFAULT 'unused',  -- unused/used/refunded/expired
  used_at           INTEGER,
  ticket_id         TEXT REFERENCES tickets(id),     -- 关联的钟单
  used_by           TEXT,               -- 核销员工
  expires_at        INTEGER,
  created_at        INTEGER NOT NULL
);

-- 平台对账表
CREATE TABLE platform_settlements (
  id            TEXT PRIMARY KEY,
  shop_id       TEXT NOT NULL,
  platform      TEXT NOT NULL,
  period        TEXT NOT NULL,          -- 2026-09
  order_count   INTEGER NOT NULL,
  gross_cents   INTEGER NOT NULL,       -- 总面值
  commission_cents INTEGER NOT NULL,    -- 平台佣金
  net_cents     INTEGER NOT NULL,       -- 应结款
  reconciled    INTEGER DEFAULT 0,
  created_at    INTEGER NOT NULL
);
```

**功能点**：
1. 收银台/客服端加"核销团购券"按钮 → 扫码或输码 → 自动带出套餐内容
2. 核销后自动创建对应钟单（套餐含多个项目时生成多个 ticket）
3. 记录平台订单号，支持按月导出对账表
4. 佣金比例可配置（抖音/美团抽成不同，通常 5%-20%）

**参考项目**：开源同类几乎都不做平台券核销（这是国内特有场景），
但核销流程可参考 `opensourcepos`(4.4k★) 的礼品卡（Gift Card）实现思路。

**工作量**：约 3-5 天。**收益**：散客营收可对账，避免平台佣金纠纷。

### P0-2 客服工作台

**现状**：`CsDashboard.tsx` 只有 8 行，直接 `return <AdminDashboard />`。
`CsOrders.tsx` 只有 19 行，是点单队列。

**问题**：客服的实际工作是**"带客入房 → 推荐项目 → 安排技师"**，
但现在的界面是**老板视角的看板**（营收、技师状态、房间状态），
客服在这个界面上**没有可执行的动作**——只能看，不能做。

**建议：为客服设计专用工作台**，以"当前正在接待的客人"为中心：

```
┌─────────────────────────────────────────────────┐
│  客服工作台                        今日接待 12 位  │
├─────────────────────────────────────────────────┤
│  【待接待】                                       │
│   ├ 张三 · 抖音团购"足疗60min" · 待核销  [核销]   │
│   └ 李四 · 会员(138****8888) 余额¥1200  [选项目]  │
│                                                   │
│  【进行中】                                       │
│   ├ 王五 · 3号房 · 足疗60min · 技师小美  [换技师] │
│   └ 赵六 · 5号房 · 推拿90min · 技师阿强  [加项目] │
│                                                   │
│  【可安排技师】按排钟顺序                         │
│   1. 小美(明星) 空闲  2. 阿强(普通) 空闲          │
│   3. 小丽(普通) 服务中(预计18:30空)               │
└─────────────────────────────────────────────────┘
```

**关键交互**：
- 一键核销团购券 → 自动带出套餐
- 报手机号查会员 → 显示余额、偏好、历史（`customers.notes` 已有"忌口、偏好"字段）
- 推荐项目：根据客人历史消费推荐（复用现有 AI 模块）
- 安排技师：显示排钟顺序 + 技师等级 + 当前状态
- **换技师**：一键换人，记录原因

**参考项目**：
- `easyappointments`(4.4k★) 的"服务提供者选择"界面
- `LibreBooking`(817★) 的 "Waitlist"（等位名单）

**工作量**：约 5-7 天。**收益**：客服从"看板"变"工作台"，接待效率提升。

### P0-3 换技师流程

**现状**：技术上可以通过 `POST /api/tickets/:id/assign` 改 `technician_id`，
但这是"派钟"语义，不是"换技师"语义。缺的是：

1. **无原因记录**：为什么换？客人不满意？技师不适配？需要统计
2. **无影响追踪**：换掉后，原技师是否有提成？服务时长怎么算？
3. **无告警**：某技师频繁被换，应该提醒管理者
4. **UI 无入口**：收银台没有"换技师"按钮

**建议设计**：

```sql
CREATE TABLE technician_changes (
  id                TEXT PRIMARY KEY,
  shop_id           TEXT NOT NULL,
  ticket_id         TEXT NOT NULL REFERENCES tickets(id),
  from_technician_id TEXT REFERENCES technicians(id),
  to_technician_id  TEXT REFERENCES technicians(id),
  reason            TEXT,              -- customer_dissatisfied | skill_mismatch |
                                       -- customer_request | other
  reason_note       TEXT,
  minutes_served    INTEGER,           -- 换人前已服务时长
  changed_by        TEXT,              -- 操作员工
  created_at        INTEGER NOT NULL
);
```

**衍生价值**：这张表能产出**技师质量报告**——
"本月被换 5 次以上的技师"、"明星技师被换率 vs 普通技师被换率"，
直接接入现有 `ai.js` 的 `score-technicians` 评分体系。

**工作量**：约 2 天。**收益**：技师质量可量化，配合分级管理。

### P1-1 技师分级体系（字段已存在但闲置）

**现状**：`technicians` 表已有两个相关字段：

```sql
level   TEXT,   -- 初级/中级/高级/技师长
is_star INTEGER  -- 是否明星技师
```

但全库检索显示，**这两个字段几乎未被使用**：
- `PosNewTicket.tsx:204` 仅显示 `{t.level}`（纯文本展示）
- 未参与**定价**（明星技师收费更高）
- 未参与**排钟**（明星技师优先 or 单独队列）
- 未参与**展示**（顾客选技师时看不到分级）

**建议**：
1. **定价联动**：`services` 表加 `star_price_cents`，或加技师等级系数
2. **排钟联动**：`/api/tickets/queue` 支持按等级分组排队
3. **展示联动**：顾客端扫码选技师时显示等级徽章 + 该技师评分
4. **提成联动**：不同等级技师提成比例不同（`services.commission_value` 目前是服务级，可扩展为技师级覆盖）

**工作量**：约 2-3 天。**收益**：让已有的分级字段真正产生价值。

### P1-2 自动排钟算法

**现状**：只有 `GET /api/tickets/queue`（查询队列），**没有自动分配算法**。
店主说"或者按照排钟直接安排技师"——这是**轮转排钟**（round-robin）。

**建议**：
```javascript
// 排钟优先级（从高到低）
1. 空闲技师中，按「上次服务结束时间」升序（久等的优先）
2. 同等等待时长，明星技师优先（如果客人未指定）
3. 排除：请假、休息、当前被换下的技师
4. 排除：刚被该客人换掉的技师
```

**参考**：`LibreBooking` 的 resource allocation 思路。

**工作量**：约 1-2 天。

## 四、已实现但需微调的环节

### 4.1 夜晚留宿

**现状**：`tickets.overnight` + 3000 分附加费，`endwatch.js` 对过夜单不按钟点提醒。

**与店主描述的差异**：店主说"客人如需夜晚留宿需要告知店里"——
这是**登记告知**性质（可能收费也可能免费），而不是固定收费项。

**建议**：`overnight` 从"固定 3000 分"改为**可配置**（0 = 免费登记，或按房间/时段定价），
并加"留宿登记表"供前台查看当晚留宿客人（安全责任需要）。

### 4.2 评价时机

**现状**：限 `completed/paid` 状态才能评价。

**与店主描述的差异**：店主说"技师服务后让客人进行评价"——
即**服务一结束就评价**，不必等到结账。

**建议**：放宽为 `completed` 即可评价（去掉 `paid` 要求），符合实际动线。

### 4.3 会员识别

**现状**：`customers.phone` 有 `UNIQUE(shop_id, phone)`，支持手机号查会员。

**建议**：收银台/客服端加"报手机号"快捷入口——输入后 4 位自动匹配会员，
显示余额/等级/偏好，一键带入钟单。

搜遍 748 个仓库，**足浴/按摩品类的成熟开源项目几乎不存在**：

## 七、核心结论

1. **本项目的问题不是"功能少"，而是"链路不完整"**。
   已有功能集中在"服务→离店"这一段，且做得比所有开源同类都专业
   （房间管理、派钟、钟单流转、储值卡、提成档位——这些通用 POS 都没有）。

2. **最大缺口是散客获客入口**。店主明确说散客来自抖音/美团，
   而代码里**团购券核销零实现**。这意味着散客营收无法对账，是经营风险。

3. **客服端是空壳**。8 行的 `CsDashboard` 直接复用老板看板，
   但客服的工作是"带客-推荐-安排"，需要的是**工作台**而非**看板**。

4. **已有字段闲置是隐性浪费**。`technicians.level` 和 `is_star` 已存在
   却不参与定价/排钟/展示，补上联动即可释放价值，成本极低。

5. **不要对标通用平台**。mautic(10.6k★)、akaunting(10k★)、frappe/hrms(8.9k★)
   功能庞大但场景错配。**借鉴思路，不照搬架构**。

6. **技术栈保持现状**。Node + Fastify + SQLite + React + PWA 非常适合
   单店本地部署：零运维、免装 App、离线可用。调研中架构最接近的
   `Store-POS`(1k★, Electron+Express+SQLite) 验证了这条路线可行。
