## 二、逐项核实

### 2.1 无房间下单：已支持

`POST /api/guest/tickets` 的 `room_id` **本来就是可选的**：

```js
// guest.js:128
const { shop_id: bodyShop, service_id, technician_id, room_id, auto_start = false, overnight = false } = req.body || {}
```

房间校验是条件式的，`room_id` 无值直接跳过：

```js
// guest.js:140-145
if (room_id) {
  const room = db.prepare(`SELECT id, status FROM rooms WHERE id=? AND shop_id=? AND active=1`)
    .get(room_id, shop.id)
  if (!room) throw new NotFoundError('room not found')
  if (auto_start && room.status === 'occupied') throw new ConflictError('房间已被占用')
}
```

落库时 `room_id || null`：

```js
// guest.js:169
`).run(id, shop.id, technician_id || null, room_id || null, ...)
```

**这意味着「顾客在大堂下单，房间待定」的场景，后端已经能跑。**

### 2.2 待派钟队列：天然包含自助单（关键发现）

```sql
-- tickets.js:210-212
WHERE t.shop_id=?
  AND t.status IN ('pending','active')
  AND (t.technician_id IS NULL OR t.status='pending')
ORDER BY t.created_at ASC
LIMIT 200
```

条件 `technician_id IS NULL OR status='pending'` 意味着：

- 顾客下单时**未指定技师** → `technician_id` 为 NULL → **自动进队列** ✅
- 顾客下单时**指定了技师**但未开钟 → `status='pending'` → **也进队列** ✅
- 顾客下单时指定技师且 `auto_start=true` → `status='active'` 且有技师 → 不进队列（合理，已在服务中）

**结论：顾客自助下单后，客服/收银无需任何额外操作就能在待派队列看到。**

实测数据库确认 `self` 单存在（当前库里有 5 条，均为测试遗留的 canceled 状态）。

### 2.3 指派接口：能力完整

```js
// tickets.js:227  POST /api/tickets/:id/assign
// body: { technician_id?: string|null, room_id?: string|null, also_start?: boolean }
```

已实现的校验：

- 钟单必须属于本店（`PermissionError`）
- 仅 `pending`/`active` 可指派
- 技师存在且 `active`（否则 `NotFoundError`）
- **技师忙碌检查**：`SELECT 1 FROM tickets WHERE technician_id=? AND status IN ('pending','active') AND id!=?`
- **房间占用检查**：同样模式
- `active` 状态下改派会**同步释放原技师/原房间**的状态
- 写入 `audit_logs`（`ticket.assign`），记录 `prev_technician_id`/`prev_room_id`

**这个接口可以直接复用，不需要改。**

### 2.4 派单 UI：收银端已有（重大发现）

`PosHome.tsx`（480 行）已经包含完整的派单交互：

- **待派钟队列**（192-248 行）：显示 `待开钟`/`上钟中·无技师` 标签、房间号、技师、价格
- **派钟弹窗**（381-468 行）：选空闲技师下拉、AI 推荐按钮、`派钟并开钟`/`确认改派` 按钮
- **自助单专区**（258-303 行）：单独列出 `fulfillment === 'self'` 的单，标记 `到店自提`/`未派技师`
- **实时刷新**（34-44 行）：监听 `ticket:created`/`ticket:assigned` 等 WebSocket 事件

**所以「客服派单」的 UI 已经存在于收银端，只是客服端（`/cs`）没有自己的入口。**

### 2.5 AI 排钟：已实现（且比预期的完善）

```js
// ai.js:442  POST /api/ai/suggest-dispatch
```

本地启发式打分（AI 关闭也能用）：

```js
let score = 50
score += (Number(t.ai_score) || 0) * 6          // 0-5 → +30
score += (Number(t.avg_rating) || 0) * 4
if (t.is_star) score += 5
score -= Math.min(load * 2, 20)                 // 近7日负载惩罚
if (同项目做过) score += 8                        // 技能匹配
if (高峰时段 && ai_score >= 4) score += 6         // 高峰优先高分
```

可选叠加 LLM 解读（`aiScheduleSuggestion`），失败回退本地。

**但这套是「智能推荐」，不是「公平轮转」。** 它优化的是「谁最合适」，
而行业排钟要求的是「谁该轮到」——两者语义不同，见 §四。

## 三、真正的缺口（已核实）

### 3.1 顾客端无法按 ticket_id 找回自己的单 ⚠️ 最高优先级

```js
// guest.js:93-94
// 必须限定房间：shop_id 单独使用会整店泄露当日钟单
if (!room_id) throw new ValidationError('room_id required')
```

所有顾客端查询**强制要求 `room_id`**，原因写在注释里（防止整店泄露）。

**但进店扫码时顾客还没有房间。** 后果：

1. 顾客下单后拿到 `ticket_id`，但**没有 `GET /api/guest/tickets/:id` 端点**
2. 顾客刷新页面 → 前端没有 roomId → **找不到自己的单**
3. 顾客端目前只把 `ticket_id` 用于提交评价，未持久化

这是**必须先补的地基**，且是**现存 bug**（与是否做大堂码无关）。

### 3.2 客服端是空壳

```
web/src/pages/cs/CsDashboard.tsx    8 行  → return <AdminDashboard />
web/src/pages/cs/CsOrders.tsx      19 行
```

`CsLayout.tsx` 只有两个 tab：看板、点单。

而客服是这套流程的中枢。不过——**收银端 `PosHome.tsx` 已有派单 UI**，
客服端可以复用组件而非从零写。

### 3.3 排钟：完全没有（已 grep 确认）

```bash
$ grep -rn "rotation\|轮钟\|next_in_line\|queue_order" server/src/
（零匹配）
```

`technicians` 表字段：

```
id, number, name, level, years, status(idle/working/break/off),
ai_score, avg_rating, review_count, is_star, specialties, bio,
avatar, webhook_url, hired_at, active
```

**没有 `rotation_order`、`last_served_at`、`rotation_skip_count` 等任何轮转字段。**

行业七种钟型（轮钟/点钟/加钟/落钟/跳钟/挂钟/留钟）一种都没建模。

### 3.4 顾客端无 WebSocket（设计如此，但需评估）

```js
// realtime/bus.js:20-24
const token = ...searchParams.get('token')
if (!token) { socket.close(4001, 'Token required'); return }
```

顾客端无 JWT，**无法建立 WebSocket**。现在靠 10 秒轮询兜底（`GuestView.tsx:74`）。

对「等待客服分配房间」这个场景，轮询延迟可接受（用户不盯着看）。
但「客服配房后顾客端自动切换」体验上轮询够用。

**如果要做 WebSocket，需要新增免登录的顾客通道**，并解决「一个连接只能看自己的单」的鉴权问题。

## 四、一个需要澄清的语义问题：AI 推荐 ≠ 排钟

现有 `suggest-dispatch` 的评分逻辑是**「谁最合适」**：

- 评分高优先
- 明星技师优先
- 负载低的优先（避免累的继续累）

行业「轮钟」的语义是**「谁该轮到」**：

- 按固定顺序轮转（公平）
- 点钟（顾客指定）通常跳过轮转，但不影响下次位置
- 加钟不改变轮转位置
- 跳钟（技师不在）需要补偿机制

**两者不冲突，但必须共存：**

| 场景 | 用哪个 |
|------|--------|
| 顾客指定技师（点钟） | 直接指派，不走轮转 |
| 顾客未指定，客服派单 | **轮转顺序**（公平） |
| 客服想优化配置 | AI 推荐（可选参考） |

**当前系统只有 AI 推荐，没有轮转。** 这会导致：不指定技师的单，
客服每次都手动挑，且倾向于挑熟悉的/高分的 → **老技师吃撑、新技师饿死**。

## 五、实施路径（基于已核实的事实）

### 第 0 步：补地基（必须先做，且是现存 bug 修复）

1. 新增 `GET /api/guest/tickets/:id` —— 单条查询
   - 鉴权：`ticket_id` 本身即凭证（nanoid(12)），额外校验 `shop_id`
   - 返回字段需脱敏评估
2. 顾客端 `localStorage` 持久化 `ticket_id`，刷新能找回
3. 新增 `/guest` 路由（不绑房间）

### 第 1 步：客服端派单台

**不要从零写** —— 收银端 `PosHome.tsx` 的派单组件可直接抽取复用：

- 待派钟队列（`queueList` 渲染逻辑）
- 派钟弹窗（`assignTicket` 弹窗）
- AI 推荐按钮

抽成共享组件 → 收银端和客服端都用。

### 第 2 步：排钟机制（新功能）

- `technicians` 加 `rotation_order` + `last_served_at`
- 空闲技师按轮转顺序排序（而非仅按 AI 分）
- 点钟跳过轮转但不影响下次位置
- 需要新迁移（`MIGRATIONS` 数组追加，现有 14 个）

### 第 3 步：顾客端状态联动

客服配房后顾客端切换视图。轮询（10s）已够用，WebSocket 为可选优化。
