## 二、关键发现：运行时是 Node 22，不是 Node 20

这是本次调研最有价值的发现，直接影响升级方案。

### 2.1 事实

```
$ node -v                    → v20.18.1      ← PATH 里的默认
$ which node                 → /usr/local/bin/node

但生产服务实际用的：
$ lsof -p <服务PID> | grep txt
  /Users/ylyg/.hermes/node/bin/node          ← v22.22.2

验证：
$ /Users/ylyg/.hermes/node/bin/node -v       → v22.22.2
$ /Users/ylyg/.hermes/node/bin/node -e "require('better-sqlite3')"  → OK
$ /usr/local/bin/node -e "require('better-sqlite3')"                → ERR_DLOPEN_FAILED
```

**结论**：`better-sqlite3` 的原生模块是为 **Node 22** 编译的（`NODE_MODULE_VERSION` 匹配 Node 22）。
服务在 Node 22 上跑得好好的；用 Node 20 反而加载不了。

### 2.2 为什么这件事重要

`@fastify/static@10` 的依赖链要求 Node ≥ 22：

```
@fastify/static@10.1.5
  └── content-disposition@3.0.0   (engines: node >= 22)
```

实测对比：

| 运行时 | `@fastify/static@10` |
|--------|----------------------|
| Node 20 | ❌ **崩溃** `ERR_REQUIRE_ESM`（Node 22+ 才支持 require() ESM） |
| Node 22 | ✅ `PROBE_OK`，静态服务 + CORS 正常 |

**因为项目本来就在 Node 22 上跑，`@fastify/static@10` 可以安全升级。**

### 2.3 但有一个隐患

项目**没有 `.nvmrc`，`package.json` 也没有 `engines` 约束**。
这意味着：如果哪天有人在 Node 20 环境下 `npm install`，
better-sqlite3 会按 Node 20 编译，服务就会挂。

**建议立即补上**（这是低成本的预防措施）：

```json
// server/package.json
"engines": { "node": ">=22" }
```

```bash
# 项目根目录
echo "22" > .nvmrc
```

### 3.5 TypeScript 5.9.3 → 7.0.2 ⚠️ 可升，需改一处

TS 7 是**编译器用 Go 重写**的版本，性能提升 8-12x（微软官方数据：
VS Code 125.7s → 10.6s）。

**实测结果**：

```
$ npx tsc --version                        → Version 7.0.2  (Node 20 下也能跑)

$ npx tsc --project <项目tsconfig> --noEmit
error TS5102: Option 'baseUrl' has been removed.
  Use '"paths": {"*": ["./*"]}' instead.
```

**唯一阻塞是 `baseUrl` 已被移除**。移除后重测：

```
$ npx tsc --project <项目tsconfig-无baseUrl> --noEmit
（无输出，0 错误）
```

**并且验证了 TS 7 确实在做真实类型检查**（不是静默跳过）：
注入 `const x: number = "string"` 后：
```
TS7:   error TS2322: Type 'string' is not assignable to type 'number'.
TS5.9: error TS2322: Type 'string' is not assignable to type 'number'.   ← 一致
```

**重要警告**（来自官方迁移指南）：
> **7.0 的程序化 API 要到 7.1 才提供**（the programmatic API that half the ecosystem
> depends on does not ship until 7.1）

这意味着依赖 TS 编译器 API 的工具（部分 ESLint 插件、类型生成器等）在 TS 7 下**可能不工作**。
本项目目前没有这类工具，但**升级前需确认**。

**建议**：可升，但优先级低于 lucide。升级步骤：
1. 移除 `tsconfig.json` 的 `"baseUrl": "."`
2. 升级 `typescript@7`
3. 跑 `tsc -b --noEmit` 确认零错误
4. 跑完整构建确认 Vite 正常

### 3.6 Tailwind 3.4.19 → 4.3.3 🔶 高风险，建议暂缓

**这是唯一建议暂缓的升级**。原因：项目深度使用了 v3 特性。

**项目当前 Tailwind 用法统计**：

| 项目 | 数量 | v4 影响 |
|------|------|---------|
| 自定义色使用（`text-tan` 等） | **501 处** | 需迁到 `@theme` |
| `border` 相关 | 528 处 | **默认边框色变了** |
| `@tailwind` 指令 | 3 条 | 需改为 `@import "tailwindcss"` |
| `@layer` 区块 | 4 处 | 语法变化 |
| 需重命名的工具类（`shadow-sm`/`rounded-sm`/`blur-sm`） | 26 处 | v4 中语义变化 |
| `outline-none` | 29 处 | v4 中重命名 |

**实测 v4 编译项目原始 CSS**：
```
$ npx @tailwindcss/cli -i input.css -o out.css
Error: Cannot apply unknown utility class `bg-white/10`.
  Are you using CSS modules or similar and missing `@reference`?
```

**但验证了迁移后可行**——用 v4 语法重写后全部通过：

```css
@import "tailwindcss";

@theme {
  --color-ink: #1a1a1a;
  --color-ink-muted: #6b6b6b;
  --color-tan: #a0826d;
  --color-paper: #fafaf7;
  --color-gold: #b8860b;
  /* ... 项目全部自定义色 */
}

@custom-variant dark (&:where(.dark, .dark *));   /* 替代 darkMode: 'class' */
```

**产出验证**（逐个检查自定义色是否生成）：
```
text-tan         ✅ 产出
bg-paper         ✅ 产出
text-ink-muted   ✅ 产出
border-tan-dark  ✅ 产出
rounded-lg       ✅ 产出
.dark\:text-gold:where(.dark, .dark *) { color: var(--color-gold); }   ✅ 暗色模式正常
```

**v4 的主要破坏性变更**（官方指南）：
1. **CSS-first 配置**：`tailwind.config.js` 被 `@theme` 取代
2. **默认边框色改变**（v3 是 gray-200，v4 是 currentColor）
3. **重命名**：`shadow-sm`→`shadow-xs`、`rounded-sm`→`rounded-xs`、`blur-sm`→`blur-xs` 等
4. **移除**：`outline-none`（改为 `outline-hidden`）
5. **浏览器要求**：Safari 16.4+ / Chrome 111+ / Firefox 128+
6. 官方提供自动化迁移工具 `@tailwindcss/upgrade`

**建议**：单独排期做，不要和其他升级混在一起。且**必须视觉回归验证**——
501 处自定义色 + 528 处 border 的改动面，光靠编译通过不足以证明没坏。

## 九、第二批执行记录（2026-10-01）

### 9.1 重要发现：`@fastify/static` 是未使用的依赖

准备升级 `@fastify/static` 时发现，**它只被 import，从未被调用**：

```js
// src/index.js:16
import fastifyStatic from '@fastify/static'     // ← 全项目唯一一处，且从未调用
```

静态文件实际由**手工实现的 `sendPublicFile`** 提供，代码注释说明了原因：

```js
// src/index.js:248
// static files served manually above to ensure cache headers are controlled
```

**所以这一项不是「升级」，而是「移除」**。这也解释了为什么第一轮调研时，
`@fastify/static@10` 要求 Node 22 这件事看起来很棘手——实际上这个依赖根本不参与运行。

**处理**：删除 `index.js` 的无用 import（已验证 20/20 回归通过）。
`package.json` 中的依赖声明建议一并移除（`npm uninstall` 需确认后执行）。

### 9.2 TypeScript 5.9.3 → 7.0.2 ✅ 已完成

**步骤**：

1. 备份 tsconfig
2. 移除 `"baseUrl": "."`（TS 7 已删除该选项）
3. `npm install typescript@^7.0.2`
4. 验证

**中间验证**：先确认「删掉 baseUrl 后 TS 5.9 仍零错误」，
再升级 TS 版本——这样把「配置改动」和「版本升级」两个变量分开，
出问题能定位到具体原因。

```
TS 5.9 + 无 baseUrl  → exit=0，@/ 别名正常解析
```
