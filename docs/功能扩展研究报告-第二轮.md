## 一、本轮最重要的发现：足浴行业的"钟"体系

上一轮报告我用通用 POS 的思路理解业务，**漏掉了足浴行业最核心的概念体系**。
这轮抓到的行业资料显示：足浴店的排钟有 **7 种"钟"**，每一种都是独立业务对象，
而本项目目前只有最基础的"派钟"，**7 种钟一种都没建模**。

### 1.1 七大钟型定义（行业标准）

| 钟型 | 定义 | 触发场景 | 本项目现状 |
|------|------|----------|-----------|
| **轮钟** | 技师按排钟号排队，来客派队首，上钟后排到队尾 | 新客、未指定技师 | 只有 `queue` 查询，**无轮转算法** |
| **点钟** | 顾客点名指定技师，跳过轮钟队列 | 回头客、朋友推荐 | 仅有 `assign` 指定，**无点钟标记/统计** |
| **加钟** | 服务中延长时长或增加项目 | 客人满意想继续 | **完全缺失** |
| **落钟** | 服务结束，技师回待岗，排到队尾 | 每次服务结束 | 有 `completed_at`，但**不参与排钟归队** |
| **跳钟** | 技师暂时跳过一轮或几轮 | 吃饭、休息、上厕所 | **完全缺失** |
| **挂钟** | 技师长时间暂停排钟 | 培训、请假、病假 | 只有 `status`，**无挂钟起止时间** |
| **留钟** | 为特定客人预留技师档期 | "我20分钟到，留6号技师" | **完全缺失** |

### 1.2 关键业务规则（行业通行做法）

**轮钟规则**：
- 技师到店签到，按**签到顺序**排入队列
- 上钟后自动排到队尾
- 落钟后必须及时归队
- 请假/休息/外出的技师**跳过，不保留位置**

**点钟规则**：
- 点钟优先于轮钟（客人点了就必须安排被点的技师）
- **每日点钟上限**（如每人每天不超过 6 个）—— 防止头部技师垄断
- 点钟技师不在时，等 15 分钟后转轮钟
- **点钟提成高于轮钟 5-10 元/个**
- 健康比例：点钟占总钟数 **30%-50%**；低于 30% 说明技师整体能力不足，
  高于 50% 说明排钟机制失效、尾部技师没饭吃

**加钟规则**：
- 加钟算**个人业绩**，提成归服务的技师
- 加钟**不影响排钟**（不因加钟多就排前面）
- **禁止私下拉客加钟**，必须前台登记，防飞单
- 加钟提成比例可比首钟高 5 个百分点（如首钟 30%，加钟 35%）

**换技师规则**（对应店主说的"客人对技师不满意会换技师"）：
- 换人后的**首钟算新技师的**
- **原技师不扣钟数**，但**记录投诉次数**
- 技师中途有事下钟：换技师继续，钟数按比例分或协商

**新技师保护期**：前 1-2 个月适当照顾，保证基本钟数，但不长期保护

### 1.3 为什么这个发现很重要

行业资料里有一句关键判断：**"技师之间的矛盾 80% 以上和钟有关"**
（索易足道研究院 10000+ 门店数据）。

这意味着**排钟公平性是足浴店管理的核心痛点**，而本项目目前：
- 有 `technicians.status`（idle/busy）和 `tickets` 表
- 但**没有排钟号、没有轮转队列、没有钟型标记**
- 结果是：无法保证公平，无法统计点钟率，无法算分类型提成

**这是比"团购核销"更底层的问题**——团购核销影响获客，
排钟体系影响**店内日常运营和团队稳定**。

## 二、团购核销：技术方案已查明

### 2.1 抖音：有官方开放 API（一手资料确认）

来源：抖音开放平台官方文档
`https://developer.open-douyin.com/docs/resource/zh-CN/local-life/develop/capability/basic/verify-introduce`

**官方接口列表**（原文）：

| 能力 | 接口说明 |
|------|----------|
| 团购核销 | 验券准备：先查询订单券列表，选择待核销券后再调验券接口 |
| 验券 | 支持抖音团购券码和三方券码核销；抖音券码需先调准备接口，三方券码可直接调 |
| 撤销核销 | 支持误核销撤销，订单状态由已使用回退为待使用，**有效期为核销后 1 小时** |
| 券状态查询 | 核销异常场景下查询券状态 |
| 券状态批量查询 | 批量查询抖音券码和三方券码状态 |

**接入要求**（原文要点）：
- 需要**开发者入驻**，区分「技术服务商」和「自研商家」两条路径
- 需申请能力：**门店管理、团购核销、对账**
- 这些能力共存于「到综行业解决方案」（到店综合，足浴属此类）
- 申请流程：登录服务商平台 → 控制台 → 我的应用 → 生活服务商家应用 →
  解决方案 → 勾选能力 → 填写使用场景 → **等待平台审核**

**官方明确的业务规则**（原文问答）：
- 部分退款：一笔订单买多张券时，**未核销的券可以退款**
- 一张券**不能验证多次**
- 一笔订单最多买 **10 张券**
- 一笔订单只有 1 个团购，可购买多份
- 撤销核销：**1 小时内**，超过则无法撤销
- **次卡支持**：商品类型选「次卡」即可，接口不变，
  验券准备接口会返回总次数/已使用次数，支持按次数撤销

### 2.3 第三方聚合方案（降低接入门槛）

来源：`https://www.yunfeiapi.com/`

云飞 API —— 为中小软件企业提供**美团、大众点评、抖音、快手**全平台团购券码核销接口：
- 一站式对接多平台验券
- 零侵入式接入
- 接口调试免费，**商用按核销成功计费**
- 自称已服务 20000+ 商家

申请开发者资质、走审核流程成本高；通过第三方聚合 API 可以快速实现。

### 2.4 行业软件商的实际做法（参考实现）

来源：云上铺（`yunvip123.cn`）—— 足浴行业收银系统厂商

**前提条件**（原文）：
1. 开通抖音企业号，上架团购产品
2. 开通抖音团购核销权限
3. 安装收银系统

**核销流程**（原文 6 步）：
1. 客人到店出示团购券码
2. 前台在收银界面点击「团购核销」
3. 扫码枪扫描券码（或手动输入）
4. 系统自动验证：券码有效则显示对应项目名称和价格
5. 确认核销 → 系统自动创建订单并关联项目
6. 订单标注「抖音核销」，月底对账时自动分类统计

**关键实现细节**（可直接借鉴）：
- **项目关联**：提前在后台把平台团购产品与系统内项目关联好，
  扫码核销时自动匹配项目，不需前台手动选择
- **对账**：日常对账看当日核销笔数/金额/项目占比；
  月度对账导出渠道汇总报表与平台后台对比，**系统自动标注差异项**
- **断网限制**：核销需联网验证，**断网无法核销**（重要约束）
- **加钟处理**：核销后加钟按正常价格收费，**加钟金额不属于团购核销范围**
- **退款处理**：需在平台先退款，再在系统做退款操作，**两边数据保持一致**
- **多门店**：各门店独立核销，总部统一查看

## 三、八大功能模块（行业标准清单）

来源：索易软件（`soesoft.net`，21年足浴行业软件商，服务 10000+ 门店）

行业公认一套完整足浴收银系统应覆盖 **8 大模块**：

| # | 模块 | 核心功能 | 本项目现状 |
|---|------|----------|-----------|
| 1 | **技师排钟管理** | 轮钟/点钟/加钟/换钟、自动计时、超时提醒、技师状态看板 | ⚠️ 仅基础派钟，7 种钟型未建模 |
| 2 | **前台开单收银** | 手牌管理、房间状态监控、消费明细自动录入、多支付方式、**班次交接** | ✅ 基本完整（有 shifts 班次） |
| 3 | **会员管理** | 储值、等级、计次卡、积分 | ✅ 有储值卡和优惠券 |
| 4 | **财务对账** | 营业日报、班次对账、**团购核销金额单独统计**、异常订单标记 | ⚠️ 缺团购核销统计 |
| 5 | **员工提成核算** | 按项目/阶梯/**点钟**/**加钟**提成、自动工资表 | ⚠️ 有基础提成，缺点钟/加钟分类 |
| 6 | **团购核销** | 美团/抖音扫码核销、金额计入报表、核销记录可追溯、**支持部分核销（多次卡）** | ❌ 完全缺失 |
| 7 | **房态管理** | 实时房态图、房间预约、**自动计费**、清洁状态管理 | ⚠️ 有房间状态，无清洁状态/预约 |
| 8 | **连锁多门店** | 总部统一价格、数据隔离、**会员跨店通用**、跨店结算分账 | ⚠️ 有多店表结构，无总部视角 |

**对照结论**：8 个模块中，本项目**完整 1 个、部分 3 个、缺失 2 个、薄弱 2 个**。

## 五、修正后的优先级建议

结合本轮发现，优先级需要调整——**排钟体系比团购核销更底层**：

```
第零阶段（最优先）— 排钟体系重构
  ├─ 排钟号 + 轮转队列（轮钟）
  ├─ 点钟标记与统计（点钟率）
  ├─ 加钟（延长时长/加项目，追加费用）
  ├─ 落钟归队
  ├─ 跳钟 / 挂钟（技师状态精细化）
  └─ 留钟（为客人预留技师）
  → 理由：行业数据显示 80% 技师矛盾源于此；且它是提成、统计、公平性的基础

第一阶段 — 团购核销（获客闭环）
  ├─ 第三方聚合 API（云飞等）或抖音官方 API
  ├─ 平台券与系统项目关联
  ├─ 核销后自动开单
  └─ 渠道对账报表
  → 理由：散客唯一入口；断网无法核销，需提示

第二阶段 — 客服工作台
  ├─ 待接待/进行中/可安排技师
  ├─ 报手机号查会员
  └─ 换技师（记录原因，原技师不扣钟数但记投诉）

第三阶段 — 提成体系细化
  ├─ 点钟/轮钟/加钟分类型提成
  ├─ 阶梯提成
  └─ 自动工资表

第四阶段 — 房态与清洁、留宿登记、连锁
```

**优先级调整说明**：
上一轮我把"团购核销"列为 P0 第一位。本轮行业调研显示，
**排钟体系应该更优先**——因为：
1. 它影响**每天**的运营（团购核销只影响散客到店那一刻）
2. 它是**提成计算的数据基础**（没有钟型标记，无法算分类提成）
3. 行业数据显示技师矛盾 80% 源于排钟，是**团队稳定性**问题
4. 团购核销依赖外部平台（审核、联网），排钟体系完全自主可控
