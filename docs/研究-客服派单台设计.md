## 一、行业调度台/派单台产品设计分析

### 1.1 参考行业与产品

| 行业 | 产品/场景 | 核心设计模式 |
|------|----------|-------------|
| 足浴/洗浴/SPA | 博卡、美业管家、有赞美业、客如云 | 房态图 + 技师列表 + 派单面板 |
| 餐饮 | 美团收银、哗啦啦 | 叫号队列 + 桌台状态 |
| 医院 | 分诊台叫号系统 | 优先级队列 + 资源分配 |
| 网约车/外卖 | 滴滴派单台、美团骑手调度 | 地图 + 实时状态 + 自动/手动派单 |
| 酒店 | 房态图（Housekeeping Board） | 网格化房间状态 + 颜色语义 |

### 1.2 核心设计模式总结

#### 1.2.1 布局：三区分离

```
┌─────────────────────────────────────────────────────────┐
│  队列区（待服务）  │  资源区（房间/技师）  │  操作区（详情）  │
│  （左 25%）        │  （中 50%）           │  （右 25%）     │
└─────────────────────────────────────────────────────────┘
```

- **队列区**：显示等待服务的顾客/工单，按等待时长排序
- **资源区**：房间状态网格 + 技师状态列表（核心视觉区）
- **操作区**：选中对象后的详情与操作面板

#### 1.2.2 房态图（Room Grid）设计

**颜色语义系统**（行业通用）：

| 状态 | 颜色 | 含义 |
|------|------|------|
| 空闲（idle） | 绿色 `#22c55e` | 可立即安排 |
| 占用（occupied） | 红色 `#ef4444` | 正在服务中 |
| 待清洁（cleaning） | 黄色 `#eab308` | 服务结束，待清理 |
| 预留（reserved） | 蓝色 `#3b82f6` | 已预订，待到店 |
| 维修（maintenance） | 灰色 `#6b7280` | 不可用 |

**网格布局**：
- 每行 4-6 个房间（根据屏幕宽度自适应）
- 房间卡片显示：房间号、当前顾客、服务技师、已用时长
- 点击房间卡片 → 右侧操作区显示详情

#### 1.2.3 队列展示与排序

**排序规则**（优先级从高到低）：
1. 等待时长（最长优先）
2. 会员等级（VIP 优先）
3. 预约时间（已到预约时间优先）
4. 创建时间（早创建优先）

**队列卡片信息**：
- 顾客姓名/手机号后四位
- 等待时长（分钟）
- 需求项目（如：足浴 90 分钟）
- 来源（到店/预约/抖音券/美团券）
- 特殊备注（如：怕痛、指定女技师）

#### 1.2.4 派单操作交互

**主流模式对比**：

| 模式 | 适用场景 | 优点 | 缺点 |
|------|---------|------|------|
| 拖拽派单 | 平板/触屏 | 直观、快速 | 触屏精度要求高、易误触 |
| 点击选中 → 点击目标 | PC/平板 | 精确、容错高 | 操作步骤多 |
| 一键自动派 | 所有场景 | 最快、零点击 | 需预设规则、灵活性低 |
| 快捷键派单 | PC | 极快 | 学习成本高 |

**推荐**：**点击选中 + 一键自动派** 混合模式（主用点击，辅以自动派）

#### 1.2.5 冲突处理

- **目标房间已被占用**：红色闪烁提示 + 声音提醒（可选）
- **目标技师已被占用**：显示技师当前状态，建议替代技师
- **并发冲突**：后端 `POST /api/tickets/:id/assign` 已含 busy 校验，前端显示错误提示

#### 1.2.6 实时性

- **WebSocket 优先**：新单、状态变更实时推送
- **轮询兜底**：WebSocket 断开时，每 5 秒轮询 `GET /api/tickets/queue`
- **新单提醒**：右上角 badge + 提示音（可配置）

## 二、关键交互设计

### 2.1 一键派单（配房 + 派技师）

**目标**：用最少点击完成「配房 + 派技师」

**流程**：
```
1. 点击队列中的顾客卡片（选中）
2. 系统自动推荐：最优房间 + 最优技师（基于排钟规则）
3. 点击「确认派单」按钮 → 完成
```

**自动推荐逻辑**：
- 房间：优先同性别房间 → 优先空闲最久的房间
- 技师：按排钟轮转 → 优先空闲技师 → 优先评分高的技师

**交互细节**：
- 选中顾客后，右侧操作区显示推荐方案
- 可手动调整房间/技师（下拉选择）
- 确认后调用 `POST /api/tickets/:id/assign`

### 2.2 按排钟自动派

**场景**：存在轮转队列，客服一键按排钟派下一位

**流程**：
```
1. 点击「按排钟派」按钮
2. 系统自动：取队列第一位 → 分配排钟中下一位技师 → 分配空闲房间
3. 显示派单结果（成功/失败原因）
```

**排钟规则**：
- 技师按「上次服务结束时间」轮转
- 跳过 break/off 状态的技师
- 支持「明星技师」优先分配（可配置）

### 2.3 换技师

**场景**：客人对技师不满意，需要更换

**流程**：
```
1. 在房间卡片上点击「换技师」
2. 系统显示：当前技师 + 可替换技师列表（同性别、空闲）
3. 选择新技师 → 确认
4. 后端：原技师状态回收 → 新技师占用 → audit_logs 记录
```

**后端对接**：
- 调用 `POST /api/tickets/:id/assign`，body: `{ technician_id: new_id }`
- 后端自动处理原技师状态回收

### 2.4 拖拽 vs 点击

| 场景 | 推荐 | 原因 |
|------|------|------|
| 平板（触屏） | 点击选中 | 拖拽精度要求高，易误触 |
| PC（鼠标） | 拖拽 + 点击 | 拖拽更直观，点击更精确 |
| 混合 | 点击为主，拖拽为辅 | 兼容性最好 |

**触屏拖拽可靠性问题**：
- 手指遮挡目标位置
- 滑动与滚动手势冲突
- 误触率高

**结论**：**点击选中为主，拖拽为辅**（PC 端可开启拖拽模式）

### 2.5 键盘快捷键（PC 场景）

| 快捷键 | 功能 |
|--------|------|
| `1-9` | 选中队列中第 N 位顾客 |
| `Enter` | 确认派单 |
| `Esc` | 取消选中 |
| `A` | 一键自动派 |
| `R` | 刷新队列 |
| `F` | 搜索顾客/房间 |

## 三、触屏/平板适配

### 3.1 触摸目标尺寸

**行业标准**：
- 最小触摸目标：**44×44 px**（Apple HIG）/ **48×48 px**（Material Design）
- 推荐：**48×48 px** 作为最小可点击区域
- 按钮间距：至少 **8 px**

### 3.2 布局响应式策略

```
桌面端（≥1280px）：三栏布局（队列 | 资源 | 操作）
平板端（768-1279px）：两栏布局（队列+资源 | 操作）
移动端（<768px）：单栏 + Tab 切换
```

### 3.3 触屏优化

- 按钮尺寸 ≥ 48px
- 列表项高度 ≥ 56px
- 避免 hover 状态（触屏无 hover）
- 使用 `touch-action: manipulation` 禁用双击缩放

## 四、信息密度与认知负荷

### 4.1 信息分层

| 层级 | 信息 | 展示方式 |
|------|------|---------|
| 常驻 | 房间状态、技师状态、队列数量 | 颜色 + 图标 |
| 重要 | 等待时长、当前服务 | 文字 + 数字 |
| 次要 | 顾客详情、历史记录 | 点击展开 |
| 临时 | 操作反馈、错误提示 | Toast / 弹窗 |

### 4.2 避免信息过载

- 房间卡片只显示：房间号 + 状态色 + 当前技师
- 技师列表只显示：姓名 + 状态 + 当前房间
- 队列卡片只显示：顾客 + 等待时长 + 项目
- 详情信息点击后展开

### 4.3 颜色语义系统

**全局统一**：
- 绿色：空闲/可用
- 红色：占用/忙碌
- 黄色：等待/待处理
- 蓝色：预留/信息
- 灰色：不可用/禁用

**技师状态**：
- 空闲（idle）：绿色
- 服务中（working）：红色
- 休息（break）：黄色
- 下班（off）：灰色

### 5.3 状态管理

| 状态 | 管理方式 | 说明 |
|------|---------|------|
| 队列数据 | TanStack Query | `useTicketQueue()`，自动缓存 + 轮询 |
| 房间数据 | TanStack Query | `useRooms()`，WebSocket 更新 |
| 技师数据 | TanStack Query | `useTechnicians()`，WebSocket 更新 |
| 选中顾客 | 本地状态 | `useState<Customer \| null>` |

| 弹窗状态 | 本地状态 | `useState<boolean>` |
| WebSocket | 自定义 Hook | `useWebSocket()`，自动重连 |

### 5.4 关键交互流程

#### 流程 1：一键派单

```
1. 客服点击队列中的顾客卡片
   → 选中顾客，右侧操作区显示推荐方案
2. 客服点击「确认派单」
   → 调用 POST /api/tickets/:id/assign
   → 成功：更新队列、房间、技师状态
   → 失败：显示错误提示（如：技师已被占用）
```

#### 流程 2：按排钟自动派

```
1. 客服点击「按排钟派」按钮
   → 系统自动：取队列第一位 → 分配排钟中下一位技师 → 分配空闲房间
2. 显示派单结果
   → 成功：显示派单详情
   → 失败：显示失败原因（如：无空闲技师）
```

#### 流程 3：换技师

```
1. 客服在房间卡片上点击「换技师」
   → 弹出换技师弹窗，显示可替换技师列表
2. 客服选择新技师 + 换技师原因
   → 点击「确认换技师」
   → 调用 POST /api/tickets/:id/assign
   → 成功：原技师状态回收，新技师占用
   → 失败：显示错误提示
```

### 5.5 与现有后端接口的对接方式

| 功能 | 接口 | 说明 |
|------|------|------|
| 获取队列 | `GET /api/tickets/queue` | 待派钟队列 |
| 获取房间 | `GET /api/rooms` | 房间列表（含状态） |
| 获取技师 | `GET /api/technicians` | 技师列表（含状态） |
| 派单 | `POST /api/tickets/:id/assign` | body: `{ technician_id?, room_id?, also_start? }` |
| 换技师 | `POST /api/tickets/:id/assign` | body: `{ technician_id: new_id }` |
| WebSocket | `ticket:created` / `ticket:assigned` / `ticket:updated` | 实时更新 |

**TanStack Query 配置**：

```typescript
// hooks/useTicketQueue.ts
export function useTicketQueue() {
  return useQuery({
    queryKey: ['ticketQueue'],
    queryFn: () => fetch('/api/tickets/queue').then(r => r.json()),
    refetchInterval: 5000, // 轮询兜底
    staleTime: 0,
  });
}

// hooks/useAssign.ts
export function useAssign() {
  const queryClient = useQueryClient();
  
  return useMutation({
    mutationFn: ({ ticketId, data }: { ticketId: string; data: AssignData }) =>
      fetch(`/api/tickets/${ticketId}/assign`, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(data),
      }).then(r => r.json()),
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: ['ticketQueue'] });
      queryClient.invalidateQueries({ queryKey: ['rooms'] });
      queryClient.invalidateQueries({ queryKey: ['technicians'] });
    },
  });
}
```

## 七、总结与建议

### 7.1 核心设计原则

1. **三区分离**：队列区、资源区、操作区清晰分离
2. **颜色语义**：全局统一的颜色系统，一眼可辨状态
3. **点击为主**：触屏友好，拖拽为辅
4. **一键操作**：减少操作步骤，提高效率
5. **实时更新**：WebSocket 优先，轮询兜底
