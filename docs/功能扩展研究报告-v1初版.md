# 足韵 yuwen-spa 功能扩展研究报告
## — 基于 GitHub 开源同类项目（748 仓库）的功能缺口分析

> 调研日期：2026-10-01
> 调研方法：GitHub Search API 8 轮 148 个关键词查询，累计 748 个仓库，
> 筛选 100★ 以上 170 个做深度分析，克隆 2 个项目读源码，抓取 7 个项目 README 功能清单。
> 对标对象：本项目 yuwen-spa（Node.js + Fastify + SQLite + React + PWA，本地部署足浴 SaaS）

---

## 一、结论速览

本项目在**核心业务闭环**（开钟-派钟-结账-报表）上已经完整，甚至比绝大多数开源同类项目更贴合足浴场景
（房间状态、技师派钟、钟单流转、储值卡、提成档位这些都是垂直行业专有概念，通用 POS 项目都没有）。

真正的缺口在**三个方向**，按投入产出比排序：

| 优先级 | 方向 | 缺口功能 | 参考项目 | 预估工作量 |
|--------|------|----------|----------|-----------|
| P0 | 顾客自助 | 在线预约 + 等位排队 | easyappointments, LibreBooking | 中 |
| P0 | 硬件对接 | 热敏小票打印（ESC/POS） | receiptline, EscPosEncoder | 小 |
| P1 | 经营深度 | 员工考勤 + 工资核算 | frappe/hrms, horilla-hr | 中 |
| P1 | 经营深度 | 营销自动化（沉睡唤醒/生日/复购） | mautic, parcelvoy | 中 |
| P2 | 门店协同 | 挂单/取单（暂存未结账单） | Store-POS | 小 |
| P2 | 数据洞察 | 客户流失预警 + 需求预测 | 现有 AI 模块可扩展 | 小 |
| P3 | 多店 | 多租户 + 总部看板 | ever-gauzy, coai | 大 |

**不建议做的**（调研后排除）：
- 完整 ERP/会计（akaunting 10k★）—— 足浴店不需要复式记账
- 数字标牌（xibo 736★）—— 场景不符，门店不需要第二块屏
- 自建 SMS 网关（textbee 3.1k★）—— 国内用企业微信/短信服务商更实际

## 三、逐个缺口详析

### P0-1 在线预约 + 等位排队

**现状**：本项目已有 `appointments.js`（预约 CRUD、确认、取消、改期）和 `tickets/queue`（派钟队列），
但**顾客端不能自助预约**，也不能远程取号等位。

**参考实现**：

`easyappointments`（4.4k★，PHP/CodeIgniter）—— 自托管预约调度的事实标准：
- 顾客端选服务 → 选技师 → 选时段 → 填资料 → 提交，全程无账号
- 服务时长自动推算可用时段（`Availability.php`）
- 工作时段规则（`Working Plans`）：按星期配置，支持轮班
- 预约缓冲时间（避免两单无缝衔接）
- Google Calendar 双向同步（`Google_sync.php`）
- iCal 订阅（`Ics_file.php`）—— 老板可用手机日历看排班
- 邮件通知 + Webhook（`Webhooks_client.php`）

`LibreBooking`（817★）—— 资源调度视角，有两个本项目可直接借鉴的概念：
- **Waitlist（等位名单）**：满房时顾客排队，有空位自动通知 —— 对应足浴店"房间满了先登记"
- **Quotas and credits（配额与次数）**：限制单个顾客的预约次数 —— 对应"每人每天最多约一次"

**建议**：
1. 顾客端加"在线预约"入口（复用现有 QR 扫码链路，无需新 App）
2. 时段可用性算法参考 easyappointments 的 `Availability`：房间数 × 技师数 双重约束
3. 加 Waitlist 表：满房登记 → 释放房间时按顺序推送通知（复用现有 notify 模块）
4. iCal 导出：`/api/schedules/export.ics`，老板订阅到手机日历

**为什么是 P0**：足浴店老板最痛的是"电话预约靠手记、到店发现没房间"。

### P0-2 热敏小票打印（ESC/POS）

**现状**：本项目 `Receipt.tsx` 是**屏幕上的 HTML 小票**，`/api/tickets/:id/receipt` 返回数据。
但收银台实际需要**打印**，目前依赖浏览器打印（排版不可控、无法驱动小票机切纸/开钱箱）。

**参考实现**：

`receiptline`（773★）—— "小票界的 Markdown"，本项目最值得集成的：
- 用纯文本描述小票，**不依赖纸宽**（58mm/80mm 自动适配）
- 编译成 ESC/POS 指令，直接发打印机
- 支持 Epson TM / Star MC / Citizen CT / Fujitsu FP 系列
- 有 **Receipt.js Designer** 可视化编辑器（可在浏览器里预览 + 虚拟打印机 hex dump）
- 支持中文（内置多语言字体映射）

`EscPosEncoder`（377★）/ `ReceiptPrinterEncoder`（332★）—— 更底层的指令构建库，
适合需要精细控制（加粗、放大、二维码、条形码）的场景。

**技术路径选择**：

| 方案 | 优点 | 缺点 | 建议 |
|------|------|------|------|
| 浏览器 WebUSB/WebSerial 直连 | 无需装驱动 | 仅 Chrome、需 HTTPS/localhost | 备选 |
| 本地打印代理（Node + node-thermal-printer） | 兼容性好、支持网络打印机 | 需在收银机装小服务 | **推荐** |
| 云端打印服务 | 无本地依赖 | 需联网，违背本地优先原则 | 排除 |

**建议**：后端加 `/api/print/receipt/:id`，用 `node-thermal-printer` 或 `receiptline` 生成指令，
通过 **TCP 9100** 发给局域网小票机（大部分小票机支持网络打印），零客户端安装。
同时保留浏览器打印作为降级方案。

**为什么是 P0**：这是**每天必用**的功能，且工作量小（1-2 天）。

### P1-1 员工考勤 + 工资核算

**现状**：本项目 `technicians.js` 有技师状态（空闲/服务中）和提成，`shifts.js` 有**收银班次**
（开班/结班/现金对账），但**没有员工考勤**（上下班打卡、迟到早退）和**工资核算**（底薪+提成+补贴）。

**参考实现**：

`frappe/hrms`（8.9k★，Python/Frappe）—— 开源 HR 的标杆：
- 考勤（Attendance）：打卡、请假、加班
- 薪资结构（Salary Structure）：底薪 + 津贴 + 扣款，组件化配置
- 薪资单（Salary Slip）：自动计算，可导出
- 休假额度（Leave Allocation）：年假/调休余额管理

`horilla-hr`（1.4k★）—— 更轻量，Django 实现，考勤界面简洁，适合参考 UI。

**建议**：
1. 技师端加"上下班打卡"按钮（复用现有技师端登录态）
2. 后台加考勤表：日期 × 技师 × 上班时间 × 下班时间 × 状态
3. 工资单：底薪（可配置）+ 服务提成（已有数据）+ 充值提成（已有 `commission-rules`）+ 全勤奖 - 迟到扣款
4. 月度工资表导出 CSV

**为什么是 P1**：老板每月都要算工资，目前靠手工汇总提成数据。本项目**已有提成数据**，
补上底薪和考勤就能自动出工资单，边际成本低。

### P1-2 营销自动化（沉睡唤醒 / 生日 / 复购）

**现状**：本项目有 `coupons.js`（优惠券）和 `reviews.js`（评价），但**没有主动营销**——
不能自动识别"30 天没来的老客户"并推送优惠。

**参考实现**：

`mautic`（10.6k★，PHP）—— 开源营销自动化龙头，核心是**行为触发的自动化流程**：
- 分段（Segments）：按条件圈人（如"余额 > 500 且 30 天未消费"）
- Campaign：触发器 → 条件 → 动作 的流程图
- 多渠道：邮件、短信、Webhook
- 评分（Lead Scoring）：按互动频率给客户打分

`parcelvoy`（539★，TypeScript）—— 更现代的替代，支持多渠道编排。

**本项目适配建议**（不需要引入 mautic，只需借鉴"分段 + 触发"的思路）：

```
自动化规则表：
  trigger_type: 沉睡唤醒 | 生日关怀 | 复购提醒 | 余额不足 | 首次到店
  条件: 距上次消费 > N 天 / 生日当天 / 消费满 N 次
  动作: 发优惠券 / 发通知 / 标记客户标签
```

现有数据完全够用：`customers` 有消费记录、`tickets` 有到店时间、`coupons` 有券。
只需加一个**定时任务**（每天凌晨跑一次）扫描客户，命中规则就发券 + 通知。

**为什么是 P1**：这是**直接增收**的功能。足浴店 60% 营收来自回头客，
"30 天没来就发券"这类动作立竿见影。

### P2-1 挂单 / 取单（暂存未结账单）

**现状**：本项目钟单一旦开始就必须走完流程。实际场景：顾客中途加钟、多人合并结账、
"先服务后付款但人先走了"—— 需要挂起。

**参考实现**：`Store-POS`（1k★）—— 本项目架构最接近的开源项目（Electron + React + Express + SQLite + LAN 多终端）：
- **Hold / resume sales**：购物车暂存，随时取回
- 快捷键：F2 付款、F4 挂单列表、Esc 关闭
- 交易历史按状态过滤（paid / held）

**建议**：`tickets` 加 `held` 状态 + `held_at` 时间戳，收银台加"挂单"按钮和挂单列表。
工作量约 1 天。

---

### P2-2 客户流失预警 + 需求预测

**现状**：本项目 `ai.js` 已有 `anomalies`（异常检测）、`forecast`（预测）、
`score-technicians`（技师评分）、`suggest-dispatch`（派钟建议）—— **AI 基础已搭好**。

**缺口**：缺少**面向客户**的洞察。可扩展：
- 流失预警：RFM 模型（最近消费/频率/金额）打分，标记高价值流失风险客户
- 需求预测：按星期 × 时段预测客流量，指导排班（现有 `forecast` 可扩展）

**参考**：这是本项目**已领先**的领域，开源同类项目几乎都没有 AI 模块。
建议自研，不必找参考。

---

### P3 多租户 + 总部看板

**现状**：`shops.js` 已支持多门店表结构，`dashboard` 有跨店聚合，但**没有总部视角**。

**参考**：
- `ever-gauzy`（8.1k★，TypeScript）—— 开源 ERP/CRM/HRM 一体化，多租户架构完整
- `coai`（9.3k★）—— 多租户 AI 平台，含计费系统

**建议**：如果目标是连锁店，才值得投入。单体店不需要，**建议推迟**。

## 六、调研结论

1. **本项目在垂直场景上已领先**。足浴/按摩品类的开源项目基本空白，
   最高星的同类项目 NexoPOS 是通用 POS，本项目在房间管理、派钟、钟单流转上更专业。

2. **最大缺口不是"功能少"，而是"闭环没延伸到顾客和硬件"**。
   顾客端只能查不能约，收银台只能看不能打。这两个是 P0。

3. **AI 模块是本项目的差异化优势**，开源同类几乎没有。应该继续加深，
   而不是去追平通用 POS 的功能（库存、会计那些本项目已够用）。

4. **不要盲目对标高星项目**。mautic（10.6k★）、akaunting（10k★）、frappe/hrms（8.9k★）
   都是通用平台，功能庞大但与足浴场景错配。**借鉴思路，不要照搬架构**。

5. **技术选型建议保持现状**。本项目 Node + Fastify + SQLite + React 的栈非常合理：
   单机部署零依赖、SQLite 免运维、PWA 免装 App。调研中架构最接近的 Store-POS
   （Electron + Express + SQLite）验证了这条路线的可行性。
