# 顾客身份与会话保持方案研究

> **背景**：yuwen-spa 是本地部署的足浴店管理系统，顾客扫码进入 H5 页面完全免登录。当前 URL 为 `/guest/room/:roomId`，所有接口强制要求 `room_id`。新需求要求「顾客进店在大堂扫码 → 选项目+技师 → 下单 → 客服分配房间」，此时顾客还没有房间号，需要解决身份识别和会话保持问题。

---

## 一、免登录会话识别方案对比

### 方案 1：localStorage/sessionStorage 存 ticket_id

| 维度 | 分析 |
|------|------|
| **优点** | 实现极简，前端 `localStorage.setItem('my_ticket', id)` 即可；无需服务端改动；刷新页面自动恢复 |
| **缺点** | 换浏览器/清缓存/无痕模式即丢失；多标签页不同步；无法跨设备；iOS Safari 7 天后可能清除 localStorage |
| **安全性** | 低。任何能访问该浏览器的人都能看到 ticket_id，进而通过 API 查看订单详情 |
| **可用性** | 高。顾客零操作成本，刷新自动恢复 |
| **实现复杂度** | 极低（前端 3 行代码） |
| **离线/弱网** | 好。纯本地存储，不依赖网络 |

**适用场景**：作为**辅助手段**，配合其他方案使用。单独使用无法满足安全需求。

---

### 方案 2：URL 携带签名 Token（推荐方案）

**设计**：下单后生成一个签名 token，顾客后续通过 URL 参数或 localStorage 携带此 token 访问。

```
GET /api/guest/tickets/:id?t=<signed_token>
```

**签名生成**：
```js
// 服务端生成
const token = crypto.createHmac('sha256', JWT_SECRET)
  .update(`${ticket_id}:${shop_id}:${created_at}`)
  .digest('base64url')
```

**校验逻辑**：
```js
// 服务端校验
function verifyGuestToken(token, ticketId, shopId, createdAt) {
  const expected = crypto.createHmac('sha256', JWT_SECRET)
    .update(`${ticketId}:${shopId}:${createdAt}`)
    .digest('base64url')
  return crypto.timingSafeEqual(Buffer.from(token), Buffer.from(expected))
}
```

| 维度 | 分析 |
|------|------|
| **优点** | 无状态，服务端无需存储 session；token 可绑定 ticket_id + shop_id + 时间戳，防篡改；可设置过期时间；URL 可分享（如发给同伴） |
| **缺点** | URL 过长（约 44 字符）；需要处理 token 过期刷新；URL 可能被截图泄露 |
| **安全性** | 中高。HMAC 签名防篡改，但 token 本身相当于 bearer token，任何拿到 token 的人都能访问。建议绑定 IP 或设备指纹（可选） |
| **可用性** | 中。顾客无需操作，但 URL 较长可能影响分享体验 |
| **实现复杂度** | 中。需要新增 token 生成/校验逻辑，但无需数据库表 |
| **离线/弱网** | 好。token 在 URL 中，不依赖服务端 session |

**增强措施**：
- Token 绑定 `shop_id`，防止跨店访问
- 设置 24 小时过期时间
- 可选：绑定 IP 段（同一局域网内 IP 变化不频繁）

### 方案 3：短码（取单码）

**设计**：下单后生成 4-6 位短码（如 `A3F9K2`），顾客在大堂屏幕上看到或客服告知。

| 维度 | 分析 |
|------|------|
| **优点** | 符合行业习惯（取餐码、手牌号）；顾客可主动报码；不依赖电子设备 |
| **缺点** | 需要顾客手动输入，操作成本高；短码空间小（6 位 base36 ≈ 21 亿，但实际可用空间需考虑碰撞）；需要服务端存储映射关系 |
| **安全性** | 低。4 位数字只有 1 万种可能，极易暴力破解。6 位 base36 约 21 亿，但需考虑有效订单数量 |
| **可用性** | 中。需要顾客记住或截图短码 |
| **实现复杂度** | 中。需要新增 `guest_sessions` 表存储短码映射 |
| **离线/弱网** | 好。短码可离线展示 |

**增强措施**：
- 使用 6 位以上 base36 编码
- 设置 30 分钟过期时间
- 限流：同一 IP 每分钟最多尝试 10 次

---

### 方案 4：手机号后四位 + 单号

| 维度 | 分析 |
|------|------|
| **优点** | 符合会员体系习惯；可关联会员信息 |
| **缺点** | 需要顾客输入手机号，操作成本高；手机号后四位只有 1 万种可能，需配合单号使用；隐私问题（手机号泄露） |
| **安全性** | 中。需要同时知道手机号和单号，但单号如果是 nanoid(12) 则很难猜中 |
| **可用性** | 低。需要输入手机号和单号 |
| **实现复杂度** | 中。需要验证手机号格式 |
| **离线/弱网** | 好 |

**适用场景**：作为**辅助验证手段**，不作为主要身份识别方式。

---

### 方案 5：设备指纹

| 维度 | 分析 |
|------|------|
| **优点** | 无需顾客操作；可识别同一设备 |
| **缺点** | 可靠性差（浏览器升级、清缓存都会改变指纹）；隐私问题（可能违反 GDPR/个人信息保护法）；实现复杂 |
| **安全性** | 低。设备指纹可被伪造 |
| **可用性** | 高（对顾客透明） |
| **实现复杂度** | 高。需要采集多个浏览器特征并计算指纹 |
| **离线/弱网** | 好 |

**结论**：**不推荐**。设备指纹更适合作为风控辅助，不适合作为主要身份识别手段。

### 方案 6：HttpOnly Cookie（匿名 Session）

**设计**：顾客首次访问时，服务端下发一个 HttpOnly Cookie（如 `guest_session=<random_id>`），服务端存储 `session_id → ticket_ids` 映射。

| 维度 | 分析 |
|------|------|
| **优点** | 对顾客完全透明；HttpOnly 防止 XSS 窃取；可设置 Secure + SameSite；浏览器自动管理 |
| **缺点** | 需要服务端存储 session 表；跨域问题（如果前端和 API 不同域）；Cookie 可能被浏览器清理 |
| **安全性** | 高。HttpOnly + Secure + SameSite=Strict 是最佳实践 |
| **可用性** | 高。顾客零操作 |
| **实现复杂度** | 中。需要新增 `guest_sessions` 表和清理机制 |
| **离线/弱网** | 好。Cookie 自动携带 |

**表结构设计**：
```sql
CREATE TABLE guest_sessions (
  id TEXT PRIMARY KEY,           -- nanoid(21)
  shop_id TEXT NOT NULL,
  ticket_ids TEXT,               -- JSON array of ticket_ids
  created_at INTEGER NOT NULL,
  expires_at INTEGER NOT NULL,   -- 24 小时后过期
  last_seen_at INTEGER NOT NULL
);
CREATE INDEX idx_guest_sessions_expires ON guest_sessions(expires_at);
```

## 二、推荐方案：URL 签名 Token + HttpOnly Cookie 双保险

### 推荐理由

1. **URL 签名 Token** 作为主要身份凭证：
   - 无状态，服务端无需存储
   - 可绑定 ticket_id + shop_id + 时间戳
   - 顾客刷新页面后，前端从 localStorage 读取 token 继续访问
   - 支持 URL 分享（如顾客把链接发给同伴）

2. **HttpOnly Cookie** 作为辅助：
   - 顾客首次访问时自动下发
   - 防止 XSS 窃取 token
   - 浏览器自动管理，顾客无感知

3. **localStorage** 作为前端缓存：
   - 存储 token 和 ticket_id
   - 刷新页面时快速恢复状态

### 实现流程

```
顾客扫码 → 进入 /guest/room/:roomId
    ↓
前端检查 localStorage 是否有 token
    ↓ 无
前端调用 GET /api/guest/session → 服务端下发 HttpOnly Cookie
    ↓
顾客选项目+技师 → 下单
    ↓
服务端生成签名 token，返回给前端
    ↓
前端存储 token 到 localStorage
    ↓
后续请求携带 token（URL 参数或 Authorization header）
```

## 三、行业实践调研

### 3.1 餐饮扫码点单

**典型流程**：
1. 顾客扫桌上二维码 → 进入点单页面
2. URL 携带桌号（如 `/table/A12`）
3. 下单后生成订单号，前端存储到 localStorage
4. 刷新页面后从 localStorage 恢复订单

**身份识别**：
- 主要依赖**桌号**（物理位置绑定）
- 部分系统使用**短码**（如取餐码 `B123`）
- 高端系统使用**手机号 + 验证码**

**安全机制**：
- 桌号 + 订单号双重验证
- 限流防止暴力枚举
- 订单号使用 UUID 或长随机字符串

### 3.2 洗浴中心手牌系统

**典型流程**：
1. 顾客前台领取手牌（如 `001`）
2. 手牌关联储物柜和消费账户
3. 消费时刷手牌记账
4. 离店时凭手牌结账

**身份识别**：
- **手牌号**是核心身份标识
- 手牌可绑定会员卡
- 部分系统使用**手环 RFID**

**安全机制**：
- 手牌号 + 消费密码（可选）
- 消费限额（超过需密码）
- 挂失机制

### 3.3 KTV 点歌系统

**典型流程**：
1. 顾客扫包间二维码 → 进入点歌页面
2. URL 携带包间号（如 `/room/VIP01`）
3. 点歌记录关联包间号
4. 结账时统一结算

**身份识别**：
- **包间号**是核心标识
- 部分系统使用**手机号 + 验证码**绑定包间

### 3.4 美容院/足疗店

**典型流程**：
1. 顾客预约时留手机号
2. 到店后前台分配房间/床位
3. 服务关联床位号
4. 结账时凭手机号或床位号

**身份识别**：
- **床位号/房间号**是核心标识
- **手机号**作为辅助验证

### 3.5 行业通用模式总结

| 模式 | 适用场景 | 优点 | 缺点 |
|------|----------|------|------|
| **位置绑定**（桌号/房号/床位号） | 固定位置场景 | 简单可靠 | 换位置后失效 |
| **短码**（取餐码/手牌号） | 移动场景 | 符合习惯 | 需手动输入 |
| **手机号 + 验证码** | 会员体系 | 可关联会员 | 操作成本高 |
| **扫码绑定** | 一次性场景 | 无需登录 | 换设备失效 |

**结论**：行业普遍采用**位置绑定 + 短码**的组合。对于足浴店场景，推荐**URL 签名 Token（位置绑定的数字化）+ 短码（辅助）**。

## 四、安全性设计

### 4.1 IDOR（不安全的直接对象引用）防护

**风险**：顾客 A 的 ticket_id 是 `abc123`，顾客 B 猜测或获取到 `abc123` 后，可以直接访问 `GET /api/guest/tickets/abc123` 查看 A 的订单。

**防护措施**：

1. **签名 Token 绑定**：
   ```js
   // 生成时绑定 ticket_id
   const token = sign(`${ticket_id}:${shop_id}:${created_at}`)
   
   // 校验时验证 ticket_id 匹配
   if (payload.ticket_id !== req.params.id) {
     throw new AuthError('无权访问该订单')
   }
   ```

2. **时间窗口限制**：
   ```js
   // Token 24 小时后过期
   if (Date.now() - payload.created_at > 24 * 60 * 60 * 1000) {
     throw new AuthError('链接已过期')
   }
   ```

3. **Shop ID 隔离**：
   ```js
   // 确保 ticket 属于当前 shop
   const ticket = db.prepare('SELECT * FROM tickets WHERE id=? AND shop_id=?')
     .get(ticketId, shopId)
   ```

### 4.2 Ticket ID 安全性分析

**当前实现**：`nanoid(12)`

**字符集**：`A-Za-z0-9_-`（64 个字符）

**空间大小**：64^12 ≈ 4.7 × 10^21

**猜中概率**：
- 假设单店每日 100 单，一年 36500 单
- 猜中概率 ≈ 36500 / 4.7×10^21 ≈ 7.8 × 10^-18

**结论**：**nanoid(12) 足够安全**，无需额外加固。但需确保：
- 不通过 URL 泄露（如 Referer 头）
- 不在日志中记录完整 ticket_id

### 4.3 限流策略调整

**现有实现**：
```js
checkRateLimit(`guest-ticket|${req.ip}`, { maxAttempts: 20, windowMs: 10 * 60 * 1000 })
```

**建议调整**：

| 接口 | 当前限流 | 建议限流 | 理由 |
|------|----------|----------|------|
| `POST /api/guest/tickets` | 20 次/10 分钟 | 10 次/10 分钟 | 防止恶意下单 |
| `GET /api/guest/tickets/:id` | 无限流 | 60 次/10 分钟 | 防止暴力枚举 |
| `POST /api/guest/reviews` | 15 次/10 分钟 | 10 次/10 分钟 | 防止刷评价 |
| `POST /api/guest/product-orders` | 30 次/10 分钟 | 20 次/10 分钟 | 防止恶意点单 |

**新增限流**：
```js
// 防止暴力枚举 ticket_id
checkRateLimit(`guest-ticket-view|${req.ip}`, { maxAttempts: 60, windowMs: 10 * 60 * 1000 })
```

### 4.4 隐私字段脱敏

**当前返回字段分析**：

| 字段 | 是否敏感 | 处理建议 |
|------|----------|----------|
| `price_cents` | 否 | 保留（顾客需要知道价格） |
| `technician_name` | 否 | 保留（顾客需要知道技师） |
| `technician_number` | 否 | 保留 |
| `service_name` | 否 | 保留 |
| `room_number` | 否 | 保留 |
| `customer_name` | **是** | 脱敏为 `张**` |
| `customer_phone` | **是** | 脱敏为 `138****5678` |
| `notes` | **是** | 不返回给顾客端 |

**建议新增脱敏逻辑**：
```js
function sanitizeTicketForGuest(ticket) {
  return {
    id: ticket.id,
    shop_id: ticket.shop_id,
    status: ticket.status,
    service_name: ticket.service_name,
    technician_name: ticket.technician_name,
    technician_number: ticket.technician_number,
    room_number: ticket.room_number,
    price_cents: ticket.price_cents,
    started_at: ticket.started_at,
    // 不返回：customer_name, customer_phone, notes, commission_cents
  }
}
```

### 5.5 实时推送方案（WebSocket 替代）

**问题**：现有 WebSocket 需要 JWT token，顾客无 token。

**解决方案**：**轮询 + 长轮询**

| 方案 | 优点 | 缺点 | 推荐度 |
|------|------|------|--------|
| 短轮询（5s） | 实现简单 | 延迟高，请求多 | ⭐⭐⭐ |
| 长轮询 | 实时性好 | 实现复杂，占用连接 | ⭐⭐⭐⭐ |
| SSE（Server-Sent Events） | 实时性好，实现简单 | 单向通信 | ⭐⭐⭐⭐⭐ |
| WebSocket + 匿名 token | 实时性最好 | 需要改造现有 WebSocket | ⭐⭐⭐ |

**推荐**：**SSE（Server-Sent Events）**

**实现**：
```js
// 服务端
fastify.get('/api/guest/events', (req, reply) => {
  reply.raw.writeHead(200, {
    'Content-Type': 'text/event-stream',
    'Cache-Control': 'no-cache',
    'Connection': 'keep-alive'
  })
  
  // 监听订单状态变更
  const listener = (event) => {
    if (event.ticket_id === req.query.ticket_id) {
      reply.raw.write(`data: ${JSON.stringify(event)}\n\n`)
    }
  }
  fastify.eventBus.on('ticket:updated', listener)
  
  req.raw.on('close', () => {
    fastify.eventBus.off('ticket:updated', listener)
  })
})
```

```js
// 前端
const eventSource = new EventSource(`/api/guest/events?ticket_id=${ticketId}`)
eventSource.onmessage = (e) => {
  const event = JSON.parse(e.data)
  // 更新 UI
}
```

## 六、多单/多场景处理

### 6.1 同一顾客多单（加钟、点单）

**场景**：顾客在服务过程中加钟，或同时点食物用品。

**设计方案**：
- 每个 ticket 独立生成 access_token
- session 中存储所有关联的 ticket_ids
- 顾客可通过 `GET /api/guest/session/tickets` 查看所有订单

**表结构**：
```sql
CREATE TABLE guest_sessions (
  id TEXT PRIMARY KEY,
  shop_id TEXT NOT NULL,
  ticket_ids TEXT,  -- JSON array: ["id1", "id2", ...]
  created_at INTEGER NOT NULL,
  expires_at INTEGER NOT NULL
);
```

### 6.2 顾客换房间（客服调配）

**场景**：客服将顾客从 05 房调到 08 房。

**设计方案**：
- 客服端调用 `POST /api/guest/sessions/:id/transfer`
- 服务端更新 ticket 的 room_id
- 顾客端通过 SSE 或轮询获取最新状态

**接口**：
```http
POST /api/guest/sessions/:sessionId/transfer
{
  "ticket_id": "abc123...",
  "new_room_id": "room456..."
}
```

### 6.3 顾客离店后数据保留策略

**建议**：
- **活跃订单**：保留 7 天（防止顾客返回查看）
- **已完成订单**：保留 30 天（用于财务对账）
- **Session 记录**：保留 7 天（用于审计）
- **过期数据**：定期清理（每天凌晨）

**清理脚本**：
```sql
-- 清理过期 session
DELETE FROM guest_sessions WHERE expires_at < ?;

-- 清理过期 access_token（通过 expires_at 字段）
DELETE FROM tickets WHERE created_at < ? AND status = 'canceled';
```

## 八、前端实现建议

### 8.1 Token 管理

```js
// lib/guestAuth.ts
const TOKEN_KEY = 'guest_access_token'
const TICKET_ID_KEY = 'guest_ticket_id'

export function getGuestToken() {
  return localStorage.getItem(TOKEN_KEY)
}

export function setGuestToken(token, ticketId) {
  localStorage.setItem(TOKEN_KEY, token)
  localStorage.setItem(TICKET_ID_KEY, ticketId)
}

export function clearGuestToken() {
  localStorage.removeItem(TOKEN_KEY)
  localStorage.removeItem(TICKET_ID_KEY)
}

// API 请求拦截器
export async function guestFetch(url, options = {}) {
  const token = getGuestToken()
  if (token) {
    url += (url.includes('?') ? '&' : '?') + `t=${token}`
  }
  return fetch(url, options)
}
```

## 十、总结

### 推荐方案

**URL 签名 Token + HttpOnly Cookie + localStorage 缓存**

### 核心优势
1. **安全性**：HMAC 签名防篡改，Cookie 防 XSS，token 绑定 ticket_id 防越权
2. **可用性**：顾客零操作，刷新自动恢复
3. **实现复杂度**：中等，无需引入新依赖
4. **可扩展性**：支持多订单、跨设备、URL 分享

### 关键设计决策
1. **Token 绑定 ticket_id + shop_id**：防止跨订单、跨店访问
2. **24 小时过期**：平衡安全性和便利性
3. **HttpOnly Cookie**：防止 XSS 窃取 token
4. **SSE 替代 WebSocket**：无需 JWT，实现简单

### 风险与缓解
| 风险 | 缓解措施 |
|------|----------|
| Token 泄露 | 24 小时过期 + 绑定 shop_id |
| 暴力枚举 ticket_id | nanoid(12) 空间足够大 + 限流 |
| XSS 攻击 | HttpOnly Cookie + CSP |
| CSRF 攻击 | SameSite=Strict Cookie |
